## 1. Процесс / Unity-редактор

- **Компиляция в play mode** → domain reload замораживает физику/инпут,
  персонаж проваливается сквозь плиты, инпут «залипает» → НИКОГДА не
  компилировать (и не править .cs) пока Илья в play; ждать выхода
  (`unity_state.py` poller / фоновый waiter), компилировать пачкой.
- **Тест-спавн через execute_code утёк в сцену** → play выбило в edit между
  проверкой и спавном → проверять `Application.isPlaying` В ТОМ ЖЕ вызове,
  что и спавн; чистить `FindObjectsByType` в edit mode.
- **«Destroy may not be called from edit mode» ×N в консоли у Ильи (29.08)**
  → соседняя проба через `execute_code` строила объект (`InteractiveObject.
  Build` → `HomeSinkCabinetCorner`) в EDIT mode, а `GridMesh.Prop` снимает
  коллайдер примитива через `Destroy` → `GridMesh.Prop` теперь edit-safe
  (`DestroyImmediate` вне play); правило прежнее: сборки/спавны пробой —
  ТОЛЬКО при `Application.isPlaying` (проверка в том же вызове), в edit
  mode чистить `DestroyImmediate` и проверять `FindObjectsByType`.
- **`execute_code`: «type GridCursor not found»** → codedom без using →
  писать полные имена `Cozy.Grid.GridCursor`, `Cozy.Character...`; удалять
  через `UnityEngine.Object.DestroyImmediate`.
- **`MaterialPropertyBlock` в инициализаторе поля MonoBehaviour** →
  «CreateImpl not allowed» на загрузке → создавать лениво в методе.
- **`pkill -f 'x_watch[.]py' && nohup ... &` одной командой** → pkill убил
  собственный shell (паттерн совпал со строкой запуска) → kill и запуск —
  РАЗНЫМИ командами.
- **Параллельная сессия сломала компиляцию (дубликат поля/переменной)** →
  не чинить чужой файл, подождать; свои дубли (напр. `examineDistance`
  добавили обе сессии) — удалить свой, принять их конвенцию.
- **Правка процедурной модели «не видна»** → геометрия строится при спавне
  → нужен перезаход в play; сначала дампить реальный объект в уровне, а не
  переделывать модель.
- **Перевес одного числа под освещение** (цвет доски 0.56/0.78/…) → эталон
  Blender — истина; не подгонять hex в Unity, править генератор/сцену.

- **`refresh_unity` «успешен», а код старый** → проект компилирует ТОЛЬКО
  после выхода из play; если Илья успел снова войти в play — сборка не
  произошла → после каждой компиляции проверять рефлексией через
  `execute_code` (наличие нового метода/значения дефа), а не верить
  `success:true`.
- **Проба в play получает `Application.isPlaying == false`** → ресурс
  `editor/state` отдаёт `is_playing:true` уже во время domain reload входа в
  play → пробы ждут не состояние редактора, а `return Application.isPlaying`
  через `execute_code` (см. `scratchpad/probe_play.py`).
- **Автономная офлайн-сборка** — `compile_check.py` из КОРНЯ ПРОЕКТА (Roslyn из
  поставки Unity) проверяет все asmdef без Unity: пользоваться ВСЕГДА перед
  ожиданием выхода из play; чужая красная сборка видна там же.
- **Снял «мёртвое» поле — упала сборка соседней сессии** (`HudUI._selectionTarget`
  ночью 28.08) → соседи начали использовать его в незакоммиченных правках →
  перед удалением членов grep по РАБОЧЕМУ дереву (не только HEAD) и `git
  status`: если файл `M` у другой сессии — не трогать, отложить.
- **`git add <общий файл>` утащил чужие незакоммиченные ханки в мой коммит**
  (28.08, дважды) → в общих файлах stage'ить ТОЛЬКО свои ханки: патч от
  `git show HEAD:file` + мои замены → `git apply --cached`; проверять
  `git show HEAD --stat` после коммита; при промахе — `update-index` +
  `commit --amend`. Ловушка скрипта: `status().strip()` съел ведущий пробел
  у ` M` и ветка «только мои» не сработала.
- **`pkill -f` по имени вотчера в одной команде с запуском** → см. выше;
  надёжнее убивать по PID, а вотчеры запускать `nohup … &` отдельной
  командой и логировать в scratchpad.
- **Ожидатель «после play» истёк/убит, а компиляции нет** → у ожидателя
  таймаут ≤ 56 мин, при `killed` перепроверять состояние вручную одним
  вызовом (`isPlaying`, `isCompiling`) и рефрешить самому.
- **Скриншот `import -window root` показал терминал, а не Blender** → окно
  Blender за терминалом; для проверки сцены надёжнее рендер превью
  (`*_preview.py` → PNG), скриншот — только для проверки кадрирования
  вотчера.
- **Ошибка компиляции «чужого» типа (`TempSource`, `HasSetpoint`)** → соседняя
  сессия посреди правки; свои файлы проверять фильтром ошибок по именам
  файлов, коммитить свои, ждать.
- **Окно Blender показывает старую сцену** → после исключения вотчер держит
  последнюю удачную сборку, stdout не сбрасывается в лог, окно под другими
  не перерисовывается → проверять по `*_work.blend`/превью headless, лог

- **`GridCursor.Selection` уже имеет поле `count` (число выделенных)** → свои
  поля называть иначе (`pieces`) (ilya-19).
- ⭐ **Сосед переписал ОБЩИЙ резолвер — сломалась фича, проверенная час
  назад** (29.08: `InteractiveObject.PartNodeOf` для «ящик выделяется
  целиком» проглотил замок щитка; поймал Илья, не сессия) → правило для
  параллельных сессий: правишь общий механизм частей/луча/осмотра
  (`PartNodeOf`, `IsPart`/`ClickPart`, `Interactor.Raycast`/`NestedPartOf`,
  `HudUI.OpenExamine`, `AttachPartCollider`) — ДО «готово» прогони в play
  чек-лист интерактива и напиши соседям, что трогал:
  щиток (дверца, замок → инвентарь, тумблеры 1→5, рычаг), Дверь#1/#2
  (полотно, замок со стороны игрока, глазок у #2), сковорода/кастрюля на
  конфорке (ховер, «Подобрать», ставится в слот), холодильник (дверцы, ящик,
  предмет внутри закрытого не выбирается), инвентарь (меню предмета,
  «Положить»). Любой новый пойманный баг — сюда В ТОТ ЖЕ ЧАС, формат
  «симптом → причина → правило» (Илья 29.08: «фиксируем баги, чтобы они
  больше не повторялись»).
- **«Правка .cs в play = reload в play»** → на этой машине

- **Тесты «падают» на пустом месте, когда рядом компилирует другая сессия**
  (30.08). EditMode-прогон посреди чужой перекомпиляции дал два ложных

## 2. Blender → FBX → Unity

- **Бутылка весила 66 800 тр. (30.08)** → `bpy.ops.mesh.subdivide` по ВСЕМ
  рёбрам цилиндра режет и окружность: 24 сегмента × 25 = 600 колонок. Правило:
  кольца по высоте задавать при построении меша (`unit_cylinder(rows)` в
  `bottle_style_scene.py`, лате из pydata), а не subdivide'ом; смотреть
  `tris=` в логе `build_kit` — предмет в руку ≈ 1–5 k, не десятки тысяч.
  После правки — 2 924 тр.

- **«Not allowed to access vertices on mesh 'Liquid' (isReadable is false)»
  в play в РЕДАКТОРЕ (30.08)** → `Mesh.vertices` импортированного FBX
  запрещён и в редакторе, не только в билде; проверка
  `isReadable || Application.isEditor` не спасает. Правило: читать вершины
  только при `mesh.isReadable`, а Read/Write моделям в `Resources` включает
  постпроцессор `Assets/Game/Editor/ModelReadable.cs` (ilya-1c) — новые FBX
  из Blender получают его автоматически.

- **Ориентацию детали в игре НЕЛЬЗЯ выводить из рендера Blender** — сверять
  только замером импортированной модели: у мойки нода `TapLever` в Unity имеет
  оси right=+X, up=мировой +Z, forward=мировой −Y (корень модели повёрнут на
  90° по X). Ось хода switch подбирается перебором ±90° по локальным X/Y/Z с
  замером габарита и центра: у рычага верным оказался +90° вокруг X (центр
  0.28 → 0.36, вверх), −90° уводило рычаг в чашу. И ГЛАВНОЕ: перед замером
  делать `AssetDatabase.ImportAsset(..., ForceUpdate | ForceSynchronousImport)`
  и `Resources.UnloadUnusedAssets()` — иначе меришь СТАРЫЙ префаб из кэша
  Resources и делаешь неверные выводы (потеряно полчаса, 2026-08-29).

- **Дверца холодильника «открыта» в покое после переноса** → экспорт
  выполнен с view-параметрами (`fridge_open 1`) → экспортёры, читающие
  `*_params.json`, экспортируют ТОЛЬКО с нейтральными параметрами
  (двери 0, лампа off), потом восстанавливают параметры просмотра.
- **Подставка слота утонула в разделителе (сковорода в полу холодильника)**
  → `Slot_Floor` был ребёнком МАСШТАБИРОВАННОГО куба (наследовал scale) →
  `Slot_*`/`slot()` — только дети корня/несмасштабированных нод.
- **Предмет висит над плитой / стоит боком в слоте** → маунт слота создан в
  системе координат корня FBX (90° X) → `mount.rotation = transform.rotation`
  хоста; оси FBX: мировой up = локальный −Z, мировой Z = локальный +Y;
  меряй пробным спавном, а не по чертежу.
- **ТЭНы не греются после переэкспорта** → соседняя сессия переименовала
  ноды трубок → `heat`/`led`/`slotNodes` в дефах держать на РОДИТЕЛЬСКИХ
  нодах (`HeaterTop,HeaterBack`), не на `Tube.001`.
- **Материалы слотов перепутались** (`zone` vs `zone_hot`) →
  `KitMaterials.Apply` матчит по ПРЕФИКСУ имени → не заводить материалы,
  один из которых является префиксом другого.
- **Модель ужалась под след** → `StretchFootprint` тянет bounds ВКЛЮЧАЯ
  ручки/выносы → `footprintSubs.y` = корпус + вынос (см. SKILL.md, длина).
- **Ширина 1.5/4.5 подквадрата — не прижать к стене/соседу** → `AxisSubSnap`
  центрует в целых слотах → ширина всегда ЦЕЛОЕ число подквадратов.
- **Деталь ниже пола после смены высоты корпуса** → проверять minY модели
  после любых правок высоты.
- **В игре стояло не то подножие дерева, что утвердили в GUI** → старый
  `build_tree.py` держал params в коде и не читал `tree_params.json` →
  экспортёр ВСЕГДА читает `<name>_params.json` (общий `build_kit.py`,
  реестр `pipeline.py`), контекст гасится ключами `hide`.
- **Сравнил FBX по размеру/md5 — «изменился»** → FBX бинарный с
  таймстампом и лежит в Git LFS (`git show` даёт указатель) → сверять
  обратным импортом в Blender (verts/tris/bounds/материалы) или пробой в
  play; бинарник прежней версии — `.git/lfs/objects/<oid[:2]>/<oid[2:4]>/<oid>`.
- **FBX-модель ужалась по вертикали на 5 % (мойка: бортик утонул в
  столешнице)** → путь префаба без `keepModelScale` гонит модель через
  `FitToHeight` → у любого FBX-объекта с точными размерами
  `keepModelScale = true` (процедурные этот путь не проходили).
- **Розетка трубы висит в 2 см от обшивки** → задняя грань габарита была
  концом колена, ушедшим ЗА плоскость стены (радиус дуги > расстояния до
  стены, напольная розетка шире отступа, корпус вентиля толще) → всё
  геометрически ограничивать отступом стены; задняя грань = контакт (см.
  BUILD.md «Рецепт „объект, врезанный в обшивку“»).
- **Скругления (`chamfer`/Bevel-модификатор) на деталях кита не доезжают —
  объект выглядит угловатым** (кровать, 2026-08-29) → `blender_kit.join()`
  делает `object.join`, а Blender сохраняет модификаторы ТОЛЬКО у активного
  объекта (первого в списке); у остальных деталей бевел молча теряется →
  скругление печь в геометрию до join: `bmesh.ops.bevel` по острым рёбрам
  (`soft_box` в `bed_double_scene.py`, отдельные offset для верхних/нижних

### Ось петли у узлов FBX-кита: вертикаль = локальная Z (2026-08-30)

- **Симптом:** дверцы навесного шкафа открываются «вниз/вбок как крышки»
  (скрин Ильи 10-57-51), хотя узлы `DoorL/DoorR` без своего поворота.
- **Причина:** корень FBX из build_kit импортируется с поворотом (270,0,0), узлы
  под ним — (0,0,0), поэтому их локальная Y смотрит в мир как −Z (горизонталь),
  а локальная Z — в мир +Y (вертикаль). Деф вращал часть вокруг `axis (0,1,0)`.
- **Правило:** для дверец объектов из Blender-кита ось вертикальной петли в дефе
  — `axis = new Vector3(0f, 0f, -1f)`. Знак `amount` для узлов БЕЗ поворота
  (кит с flip в мешах, как шкаф): полотно на +X от петли (петля слева) →
  ОТРИЦАТЕЛЬНЫЙ, полотно на −X (петля справа) → ПОЛОЖИТЕЛЬНЫЙ (Unity левая:
  +θ вокруг +Y уводит +X в −Z, к комнате). У холодильника знаки обратные
  (`FridgeDoor` −100 при полотне на −X), потому что там flip сделан поворотом
  узла в сцене и локальный X узла смотрит в мир −X — не копировать знаки между
  объектами с разным способом flip (2026-08-30: шкаф открылся «внутрь»).
  Проверка пробой префаба:
  `node.TransformDirection(Vector3.up)` должен быть горизонтален, `...forward` —
  (0,1,0). Не «чинить» это в сцене поворотом узла — узлы кита без поворота.

### Blender-сцены: фаска, превью и «где же деталь» (2026-08-30)

- **Симптом:** мелкая деталь (кнопка 10×5×1.6 см на панели холодильника) не видна
  ни в превью, ни в GUI. **Причина:** `cube(..., chamfer=True)` — фаска (BEVEL
  фиксированной ширины) больше половины толщины бокса, меш вырождается.
  **Правило:** тонким боксам (< ~3 см) фаску не ставить; либо ширину фаски считать
  от минимального размера.
- **Симптом:** в своём крупном плане (workbench) все детали одного серого цвета,
  «материал не применился». **Причина:** workbench в режиме MATERIAL красит по
  `material.diffuse_color` (viewport-цвет), а сцены задают только нодовый Base
  Color. **Правило:** цвета проверять рендером EEVEE (`BLENDER_EEVEE_NEXT`,
  `taa_render_samples` 16 хватает) или задавать `diffuse_color` в `material()`.
- **Симптом:** «деталь пропала» по превью пайплайна. **Правило:** прежде чем
  править сцену — headless-проба: exec сцены с params и печать `name / type /
  matrix_world.translation / dimensions / active_material` нужных объектов
  (образец — `scratchpad/fridge_probe.py` этой сессии). Камеры превью смотрят
  на объект целиком и мелочь на задней стенке могут не показать; для проверки
  детали ставить свою камеру ВНЕ корпуса (камера внутри стенки даёт сплошной
  серый кадр).

### Материалы кита кэшируются на сессию: правка json не видна сразу (2026-08-31)

- **Симптом:** в `<model>-materials.json` поменяли цвет/альфу, модель пересобрали,
  а в игре материал прежний. Свежий пример: плёнка масла `PanGrease` осталась
  непрозрачной, хотя в json уже стояла `alpha: 0.35`.
- **Причина:** `KitMaterials` держит словарь `_sets` «путь к json → готовые
  материалы» на всю сессию редактора и не перечитывает файл при его изменении
  (в момент замера в нём лежало 28 наборов). Данные и код при этом верные.
- **Проверка:** сбросить кэш рефлексией (`_sets` → `Clear()`) и применить
  материалы заново: если стало правильно, дело в кэше. Замер после сброса:
  `baseA 0.35, surface 1, queue 3000` — прозрачный материал появился.
- **Правило:** после правки json ждать перекомпиляции (domain reload) или
  перезахода в play; при проверке замером сначала чистить `_sets`, иначе
  измеряешь прошлую сессию, а не текущие данные.

### Заглушка из Blender остаётся видимой поверх живого текста (2026-08-31)

- **Симптом:** Илья вырубил электричество, холодильник не работает, а на табло

- **Замер в play:** живой мировой текст работает правильно (показывал «+11°»,

  `Interactor.ExamineHost` (`PartsActive`) → объекту с частями нужен
  `examinable = true` (мойка, вентиль); в пробах — ставить `ExamineHost`.
- **У объекта с рычагом в панели кнопка «Открыть/Закрыть»** → правило Ильи:
  таких кнопок нет, действие — клик по части в осмотре →
  `PowerFeature.HasLever` (есть `powerParts`) глушит `Buttons`.
- **Продукт кликался СКВОЗЬ стенку прибора (30.08, яйцо в кастрюле)** →
  вложенный объект всегда выигрывал у хозяина. Правило: содержимое видно
  только ЧЕРЕЗ ГОРЛОВИНУ — луч должен войти в хозяина сверху
  (`Interactor.ThroughOpening`, нормаль хита `y >= 0.4`); сквозь воду видно
  (у жидкости нет коллайдера), сквозь борт — нет.
- **У продукта внутри прибора была кнопка «Переместить» (30.08)** →
  `PickupFeature` не даёт её продукту с контейнером: яйцо из кастрюли и
  порция со сковороды перекладываются раскладкой. Отдельно лежащий продукт
  переносится как раньше.
- **Осмотр тумбы под мойку — камера «сильно приближена» (30.08, Илья: «да
  блин, опять»)** → `CameraFollow.ClearDistance` (сфера-каст от фокуса назад,
  чтобы камера не входила в стены) исключал только ДЕТЕЙ хоста, а мойка —
  отдельный `InteractiveObject` (hostPart) внутри тумбы: её коллайдер
  ловился в 0.18 м от фокуса, и базовые 5.1 м схлопывались до 2.5 →
  исключать и объекты, ВЛОЖЕННЫЕ в хост (`Container == host` — предметы в
  слотах/встроенные, `HostObject == host` — hostPart-части). Правило: любой
  каст/оверлап «вокруг хоста» обязан игнорировать его вложенные объекты, а
  не только его иерархию.
- **Камеру «выбрасывает» при закрытии осмотра** → колесо/Q/E в осмотре
  крутили СКРЫТУЮ обычную дистанцию → гейт зума и Q/E при `_examine`
  (ilya-03).
- **Части (дверца щитка) кликаются ВНЕ осмотра после смерти в осмотре** →
  `Interactor.ExamineHost` оставался установленным при закрытии панели
  осмотра/смерти → `HudUI.Update` сбрасывает осмотр при смерти и чистит
  `ExamineHost`, когда панель осмотра закрыта (ilya-03, 28.08). Любой новый
  выход из осмотра обязан обнулять `ExamineHost`.

- **Дверца щитка / рычаг вентиля кликаются ВНЕ осмотра (29.08)** →
  `PartsActive` сравнивал `ExamineHost == HostObject`: у объекта без хоста
  оба `null` ⇒ true → любое сравнение с nullable-хостом сначала гейтить
  `ExamineHost != null`.
- **MissingReferenceException на MeshRenderer после смены состояния
  продукта** → `InteractiveObject.SwapModel` уничтожает старую модель, а
  компоненты держат `Renderer[]`-кэши (`FallToSupport._rends`,
  `WorldFollowUI._rends`) → любой кэш рендереров объекта обязан
  перечитываться, если элемент стал null; новые кэши на объектах не
  заводить без такой проверки (29.08, яичница на конфорке).
- **Часть врезного hostPart-объекта ниже столешницы не выделяется** (пробка
  мойки, 29.08) → луч первым бьёт солидный коллайдер хозяина-тумбы, а второй
  проход `PartColliderOf` искал части только у самого хозяина →
  учитывать части hostPart-ов хозяина (`hp.HostObject == host`) и
  переключать цель клика на них.
- **Спавн объекта с единственным рендерером, выключенным на Build**
  (лужа: нода `Blob` = объём, спрятана при 0 л) → `FurnitureModel.Combined`
  падает на пустом массиве → прятать через `Renderer.enabled`, не
  `SetActive` (иначе `GetComponentsInChildren<Renderer>` пуст).
- **Вода/струя мойки «на столешнице», а не на дне** (29.08) → рефакторинг
  соседа добавил `_nodeBase` для позиции ноды уровня, но ветка
  синтезированного холдера (`BuildBoxVolume`, мойка) его не заполняла →
  при подмене `_node` на созданный объект обновлять ВСЕ кэши позы
  (`_nodeBase`, `_meshBounds`, `_fullScale`, `_ghost*`); проверять пробой
  `FullWorldBounds().min.y` == дно чаши.
- ⭐ **Тот же null-против-null, второй раз (30.08): продукты внутри посуды
  выделяются в ОБЫЧНОМ режиме.** `Interactor.InsideExamined` шла вверх по
  цепочке `Container` и на объекте без контейнера сравнивала `null` с
  `ExamineHost == null` — `ReferenceEquals(null, null)` = true, значит
  «внутри осматриваемого» оказывалось ВСЁ вложенное сразу, и фильтр
  продуктов молча не работал. Лечение: `if (ExamineHost == null) return
  false;` в начале и `io.Container != null` в условии цикла.
  **Правило (повтор 29.08, `PartsActive`):** прежде чем сравнивать что-то
  с nullable-хозяином (`ExamineHost`, `HostObject`, `Container`), гейтить
  сам хозяин на null — и делать это ДО цикла, иначе проверка «протекает» на
  последнем шаге обхода. Проверять зондом три случая: осмотра нет → False,
  осматриваем хозяина → True, осматриваем другой объект → False.

- ⭐ **В осмотре наведение на еду в сковороде отдавало саму сковороду**
  (30.08). В `Interactor.Raycast` роль «вложенного кандидата» занимал ПЕРВЫЙ
  встреченный вложенный объект — а сковорода сама вложена в плиту, поэтому
  становилась и ближайшим, и вложенным; дальше ранний выход
  `nearest != null && nestedIt != null && distance > best + PartTie`
  обрывал перебор ДО хита по яичнице. На тарелке (она ни в чём не лежит)
  тот же код работал — отсюда «на тарелке можно, на сковороде нельзя».
  **Правило:** «вложенным» считать только то, что лежит ВНУТРИ текущего
  ближайшего или глубже (`InteractiveObject.NestedInside` — цепочка
  Container на любую глубину), и по той же цепочке делать финальную замену;
  ранний выход из цикла луча допустим лишь когда кандидат уже настоящий
  победитель. Смотреть на такие правила ВСЕГДА в паре «носитель ни в чём не
  лежит / носитель сам вложен» — второй случай и ловит баг.
- **Зонд, подменяющий позицию мыши, меряет мимо** (30.08): `InputState.Change`
  на `Mouse.current.position` затирается реальным курсором на ближайшем
  `InputSystem.Update()`, и «повтор бага» получается на СЛУЧАЙНОЙ точке
  экрана. **Правило:** чтобы проверить наведение зондом, двигать не мышь, а
  КАМЕРУ — развернуть её так, чтобы луч через фактический курсор шёл в цель
  (`Quaternion.FromToRotation(localDir, worldDir)`), и звать настоящий
  `Raycast`; позу камеры и игрока возвращать в try/finally.

### Камера осмотра: зазор не должен ломать кадр (2026-08-30)

- **Симптом:** «камера подъезжает вплотную» у объектов, над/рядом с которыми
  что-то стоит (кофемашина под навесным шкафом, стояк у стены).
- **Причина:** подтяжка камеры к ближайшей помехе (`KeepExamineClear`) не имела
  нижней границы; расчётная дистанция кадра при этом верная.
- **Правило:** любую «подтяжку по зазору» ограничивать долей расчётной
  дистанции (сейчас 0.7) и искать ракурс в обе стороны; помеху пускать за
  ближнюю плоскость. Диагностика: сравнивать `_examineDist` с
  `_examineBaseDist`, а не смотреть глазами.

## 4. Постановка «Положить» / слоты / контейнеры

- ⭐ **Подпись действия сделали мировым 3D-текстом — её не видно.**
  `WorldLabel.Make(..., size (3,1), height 0.07)` при кегле 10: рамка в
  ТРИ ЕДИНИЦЫ при глифах в десять — текст переносился по каждому слову, а
  с игровой камеры (12 м) был высотой в несколько пикселей. Правило: подписи
  действий — только UI-чип у силуэта (см. UI.md «Интерактивные подписи»),
  3D-текст оставляем табло на корпусе приборов.
- ⭐ **Объект «не ловится» курсором там, где у него нет коллайдера.** У мойки
  коллайдеры стояли только на бортиках и кране, чаша пустая — луч проходил
  насквозь, и «Вылить» срабатывало лишь на узкой грани (замер: 9 попаданий из
  49 лучей по площади мойки). Правило: если объект — ПРИЁМНИК (в него льют,
  кладут, выбрасывают), его рабочая площадь обязана иметь коллайдер;
  проверяется сеткой лучей по габаритам, а не на глаз.
- ⭐ **Красный красил и СОДЕРЖИМОЕ.** Пока посуда невалидна, краснел весь
  набор — включая порции внутри; хуже того, порция, переложенная в момент
  красноты, уезжала в тарелку УЖЕ КРАСНОЙ и оставалась такой, пока посуда не
  станет валидной. Правило: подсветка валидности — только у самого носимого
  предмета, никогда у его содержимого («яйца никогда не могут быть
  красными» — Илья).
- ⭐ **Носимое проваливалось в посуду.** Подъём предмета на опору ограничен
  потолком в 3 см (`BaseRaiseMax`), а стопка тарелок выше — сковорода
  оставалась на уровне столешницы и резала стопку насквозь. Правило: над
  посудой предмет поднимается на ЕЁ верх без потолка (`VesselTopUnder`);
  ставить туда всё равно нельзя, но пересечения нет. Отрисовкой «поверх мира»
  такое не лечится — пробовали, вышла плоская наклейка без света.
- ⭐ **Прозрачность «над посудой» врала.** Правило «над посудой всегда
  прозрачный» казалось верным на сковороде, но на пачке яиц над тарелкой
  давало прозрачность там, где положить НЕЛЬЗЯ. Правило точнее: прозрачность
  означает «приёмник примет то, что несём» (пусть и без места сейчас), иначе
  красный.
- ⭐ **Призрак искал место СВОИМ расчётом.** `ShowLayoutGhosts` считал
  занятость слота отдельной проверкой, и для стопки тарелок слот над
  тарелкой выходил занятым ею же самой — блюпринта не было. Правило: призрак
  и постановка обязаны спрашивать ОДНУ функцию (`LayoutFreeSlot`), иначе
  показанное и сделанное расходятся.
- ⭐ **UI цеплялся за прошлую цель.** `WorldFollowUI` кэширует рендереры
  силуэта и пересобирал их только когда те умирали. У подписи действия цель
  меняется на лету — и подпись «Вылить» уезжала к тарелкам в полэкрана от
  несомой кружки. Правило: кэш, привязанный к цели, обязан сбрасываться при
  СМЕНЕ цели, а не только при её смерти.
- ⭐ **Луч упирался в хозяина и не доходил до части.** Мойка — часть тумбы, а
  корпусный бокс тумбы сплошной и накрывает вырез: из 49 наведений по
  площадке мойки в мойку попадало 10. Правило: часть-приёмник ищется среди
  ВСЕХ хитов луча и выигрывает у своего хозяина (как вложенный предмет).
  Ловить часть «по точке попадания в хозяина» мало — точка лежит вне её.
- ⭐ **Состояние готовки не сохранялось.** В сейве объекта поля под него не
  было, а `CookProgress` всегда стартовал с первого состояния: жареное яйцо
  после загрузки уровня снова становилось сырым. Правило: всё, что меняется в
  игре и видно глазом, обязано попадать в сейв; связь с доменом — через хук
  (`InteractiveObject.RestoreCookState`), чтобы ядро не знало про кулинарию.
- ⭐ **Потолок кадрирования сломал осмотр крупных объектов.** Чтобы «приблизить
  тумбу», дистанцию осмотра ограничили сверху (2.2 м) — и всё крупное стало
  подъезжать вплотную. Правило: дистанцию осмотра меняем КОЭФФИЦИЕНТОМ
  заполнения кадра (масштабирует пропорционально) или числом в дефе
  конкретного объекта, но не общим потолком. И сперва мерить: у плиты и тумбы
  решает кадрирование по габаритам (3.92 и 5.51), а не число в каталоге.
- ⭐ **Предмет В РУКАХ считался опорой и поверхностью.** Проносишь сковороду
  над тарелкой — тарелка подпрыгивает ей навстречу: проверка опоры
  (`FallToSupport`) видела носимый предмет как поверхность и «ставила» тарелку
  на него (замер: опора 1.150 → 1.192, подъём 4.2 см каждые полсекунды). Тот
  же класс, что и «камера ныряет в плиту», где носимая сковорода считалась
  препятствием. Правило: НОСИМОЕ НЕ УЧАСТВУЕТ НИ В ЧЁМ — ни опора, ни
  препятствие, ни цель; проверять через `GridCursor.I.Carried(transform)`.
- ⭐ **«Подобрать» уничтожает объект вместе с содержимым.** У посуды с едой
  кнопка убрана: `PickupFeature` делает `Destroy(host)`, и яичница внутри
  исчезала бы молча. Переносить руками по-прежнему можно — на то и подача.
  Признак — `InteractiveObject.HasContents`, в попапе видно строку «Внутри: N».
- ⭐ **Массовая замена по подстроке переписала и САМ хелпер.** Вводя
  `GridCursor.CursorRay(cam, mouse)` вместо 14 копий
  `cam.ScreenPointToRay(mouse.position.ReadValue())`, автозамена попала и в
  тело новорождённого хелпера: он стал вызывать сам себя. Компилируется
  молча, падает стеком в рантайме. Правило: после любой массовой замены
  grep-нуть определение изменённого символа и посмотреть на него глазами;
  замену тела метода, которое ты только что создал, исключать явно.
- ⭐ **Зонд, меняющий состояние сцены, обязан возвращать его в `finally`.**
  Зонд расставлял игрока по 450 позициям и упал посреди цикла на неверном
  имени поля — игрок остался в пустоте и улетел на Y = −23000. Следующий час
  замеры показывали «везде снаружи», и это выглядело как регрессия сканера
  видимости. Правило: перенос игрока/объектов только в try/finally с
  возвратом, и после переноса — `Physics.SyncTransforms()` (автосинк в
  проекте выключен, иначе физика отвечает по старой позиции).
- ⭐ **`Mathf.Round` округляет К ЧЁТНОМУ, а сетка — вверх.** Формул
  «мир→клетка» было две: `GridSnap.Cell` на `RoundToInt` и
  `GridManager.WorldToCell` на `FloorToInt(v + 0.5)`. Ровно на границе клетки
  они давали РАЗНЫЕ клетки, а объекты стоят именно по линиям сетки. Сведено к
  одной формуле (вверх) + тест `GridSnapTests`. Правило: любая «одна и та же»
  формула живёт в одном месте, даже если она в одну строку.
- ⭐ **Объект «ловится» курсором В СТОРОНЕ от себя — бокс по всей модели.**
  Сковорода выделялась в 25 см сбоку: модель сшита в Blender в ОДИН меш
  (`join`), общий бокс вышел 0.94 × 0.60 м при чаше 0.60 и ручке 6 см, и
  пустые углы у ручки ловили луч. Лечится составным коллайдером: у моделей с
  отдельными узлами — `colliderNode` через запятую (плита, мойка), у сшитых
  мелких предметов — бокс НА КАЖДЫЙ ПОДМЕШ (материальный слот = деталь;
  `Mesh.GetSubMesh(i).bounds` доступен и при `isReadable=false`). Правило:
  коллайдер повторяет силуэт, а не габарит. При обходе мешей ОБЯЗАТЕЛЬНО
  отсеивать клоны обводки (`OutlineMask`/`OutlineBand`, до 19 штук) и
  вложенные объекты (яйца в сковороде) — иначе боксов станет вдесятеро больше
  и они уедут по чужим мешам.
- ⭐ **`x != host` при `host == null` = «подходит любой».** Цель подачи
  бралась лучом, а вложенный приёмник искался как `io.Container != host`;
  при пустом луче `host` был null, и условию удовлетворял ЛЮБОЙ свободный
  приёмник — носимый прибор оставался прозрачным всё время, пока рядом стоят
  раковина или ведро, и не гас после клика. Правило: сравнение с целью,
  которая может быть null, ВСЕГДА под проверкой `host != null`, а вложенный
  приёмник обязан ещё и попадать под курсор (точка луча в его габаритах +
  запас 25 см).
- ⭐ **ЕДА В ПРИБОРЕ НЕ ПРОПАДАЕТ — общее правило для ВСЕХ приборов.** Два
  случая, оба ловились на яичнице (2026-08-29):
  (1) содержимое ВЫПАДАЛО на пол при переносе — луч опоры `FallToSupport`
  стартует внутри коллайдера хозяина и его не видит; лечится тем, что предмет
  с `Container != null` не падает вовсе;
  (2) содержимое УХОДИЛО ЦЕЛИКОМ по одному клику — подача перекладывала все
  порции разом, и игрок читал это как «еда пропала»; подача идёт ПО ОДНОЙ
  порции за клик, призрак тоже один.
  Новый прибор/ёмкость обязан пройти обе проверки: перенёс с содержимым —
  доехало; кликнул по приёмнику — ушла ровно одна порция.
- **Содержимое ёмкости выпадает на пол при переносе** (яичница из сковороды)
  → у вложенного предмета работал `FallToSupport`, а его луч опоры СТАРТУЕТ
  ВНУТРИ коллайдера хозяина и потому его не видит: «опоры нет» → падение на
  пол, предмет отвязывается и остаётся на старом месте → предмет с
  `Container != null` не падает вовсе (`FallToSupport.Nested`). Правило общее:
  вложенное едет с хозяином, держит его хозяин. 2026-08-29.
- **Предмет висит над плитой** → см. §2 маунт слота; плюс подставка
  (`SlotPad`) ≥ 0.44 и центрирование в слоте.
- **Сковорода ниже диска конфорки** → подставка меньше следа → пад
  `max(size, 0.44)`.

- **Декор-эффект, приклеенный к объекту, ломает постановку (30.08)** →

  (Depth+Jitter), доски в среднем ниже → утопление в рельеф на
  `min(толщина−1 см, 2·DepthJitter)` (ilya-03).
- **Навесной модуль кухни красный над плитой и тумбой** (30.08). Две причины
  сразу. 1) `KitOverlapBlocked` пробивает занятость боксом У ПОЛА
  (`floorY + ProbeY`, ±`ProbeHalfY`) по следу объекта — для напольных модулей
  верно, а настенный висит НАД линией, и под ним всегда стоит кухня ⇒ красный
  где угодно. Лечение: у `mount == Wall` проба идёт по собственному телу
  объекта на его высоте (`PosedBounds`). 2) `hangFixed = true` в дефе выключает
  ветку `freeWall`, а с ней — посадку на стену (`WallTuck`/`SeatBackToWall`),
  поворот по нормали стены и высоту от курсора: объект висит на фиксированной
  `wallHeight`, спиной не к стене, и `WallBehind` его отвергает.
  **Правило:** настенному объекту со свободным размещением `hangFixed` не
  ставить; любую проверку занятости для не-напольного объекта мерить на ЕГО
  высоте, а не у пола.

- ⭐ **«Почти всегда красная» постановка внутрь секции с дверцами** (30.08).
  Проверка `SlotFits` требует, чтобы КОРОБКА предмета целиком лежала в
  площадке слота ± допуск, а площадка у навесного шкафа 42–48 см при тарелке
  40 см: валидная позиция ловилась в пределах ±1 см от центра, курсором в
  такое не попасть. Замер сетки 9×9 по четырём секциям: 0–15 валидных из 81.
  **Правило:** проверка, которую игрок обязан удовлетворить ТОЧНЫМ
  наведением, — плохая проверка; вместо отказа предмет надо ДОВОДИТЬ
  (`ClampIntoSlot` съезжает внутрь площадки, не влезает вовсе — встаёт по
  центру). Стало 324 из 324. Второй слой той же проблемы: стена, на которой
  висит хозяин, считалась помехой его содержимому — внутри секции место
  определяет хозяин, стеноподобное не помеха.
- **Доводка ровно на границу допуска = отказ** (30.08): сдвиг предмета
  точно на `pb.min - Tol` попадает в сравнение `b.min < pb.min - Tol` и
  отбрасывается ошибкой округления float. **Правило:** доводить внутрь
  ОСНОВНОЙ границы, а допуск оставлять запасом сверху, а не целиться в него.

- **«На вторую полку ничего не кладётся»** (30.08) — и это НЕ про допуски
  слота: в центре площадки все проверки проходили. До полки не доходил ЛУЧ

  горизонтальная грань по общему правилу считается опорой, и предмет ложился
  НА шкаф. **Правило:** верх НАСТЕННОГО объекта опорой не считается (он висит
  под потолком, целятся в него, когда хотят внутрь); полку без дверец это не
  задевает — у неё нет слота глубже по лучу. **Приём:** когда «не ставится», а
  сами проверки в нужной точке зелёные, виновата не валидация, а ПУТЬ ДО
  ТОЧКИ — смотреть, что первым ловит луч курсора и какую поверхность выбрал

### Проба постановки на пад слота ловит объект, стоящий в слоте (2026-08-30, ilya-42)

- **Симптом:** после введения `acceptsObjects` проба в play показала
  `Slot_Carafe` кофемашины → `blocked=True`, пады фильтра и бака — «можно»;
  выглядело как поломка особого пути слотов.
- **Причина:** в пробе `OnVessel` вызывался с `exclude = null`, а в слоте

  выше пада), `hit1 Slot_Carafe`. В реальной постановке переносимый объект
  всегда передаётся как `exclude` — с ним пад даёт «можно». Бага в игре не
  было, ошиблась проба.
- **Правило:** пробуя постановку на пад/поверхность, передавать `exclude`
  = объект, который «в руке», или пробовать ПУСТЫЕ слоты; перед выводом
  «слот сломан» — дамп ВСЕХ хитов луча (`RayPick.Down` сортирует по
  дистанции) с именами коллайдеров. Заодно закреплено: первое попадание
  луча в пад `ContainerSlot` в `OnVessel` ⇒ сразу `return false` (особый
  путь слота), а не `continue` дальше в корпус носителя.

### Часть в вырезе хозяина ловится только «по краям» (2026-08-30, ilya-42)

- **Причина:** коллайдеры объекта — боксы по нодам `colliderNode`; у тумбы

  тумба первой, из них у 5 мойка сразу за ней.
- **Правило:** кликабельная `hostPart` побеждает СВОЕГО хозяина, если луч
  вошёл в хозяина по верхней грани над её следом и дальше попал в неё

  следом» часть перехватывала лучи через переднюю грань корпуса — ведро в
  нише тумбы стало отдавать мойку (замер ilya-71). Правило живёт в чистой

  ловит столешницу) — если понадобится, столешницу/каркас тумбы делить на

### Стопка в закрытой секции: верхние предметы выделяются сквозь дверцу (2026-08-30, ilya-42)

- **Симптом:** «в навесном шкафчике в закрытых полках можно сквозь стену
  выделять и кликать объекты» — повтор старой баги, но только для СТОПКИ
  тарелок: нижняя тарелка не ловится, верхние — ловятся.
- **Причина:** у верхних тарелок `Container` = тарелка под ними (стопка), а
  `ContainerSlot.HoldsClosed` искал слоты только у ПРЯМОГО контейнера — у
  тарелки слотов нет → «не заперто» → `Interactor.SkipHit` пропускал.
  Проба в play: три тарелки на одной полке, `holdsClosed` = True/False/False.
- **Правило:** «заперт» наследуется по цепочке контейнеров —
  `HoldsClosed(item)` при незапертом/отсутствующем слоте спрашивает
  `HoldsClosed(item.Container)`. Любой новый вид вложенности (стопка, предмет
  в предмете, раскладка) обязан проходить проверку «сквозь закрытую дверцу
  не выделяется» — прогонять пробу по ВСЕМ предметам внутри секции, не по
  первому.
- **Симптом (Blender/игра):** полупрозрачный призрак под полупрозрачной водой
  не виден. **Причина:** два blended-материала — вода рисуется поверх
  призрака, плюс цвет призрака ≈ цвет воды. **Правило:** призрак под водой —
  насыщенный синий, α ≥ 0.8, дизеринг/hashed вместо blend (в Unity —
  непрозрачный шейдер с dither или очередь после воды).

### Статус «Работает» от переключателя, который не «работа» (2026-08-30, ilya-42)

- **Симптом:** у мойки висит статус «Работает», хотя вода из крана не течёт

### «Через горловину» отрезало содержимое шкафов (2026-08-30, ilya-42)

- **Откуда взялось:** правило `Interactor.ThroughOpening` появилось в задаче ПРО
  ПРОДУКТЫ — «яйцо не должно кликаться сквозь чёрный борт кастрюли» (Илья
  вспомнил сам: «это когда мы для продуктов делали»). Для посуды оно верное.
- **Симптом:** «не могу выбрать ничего внутри других объектов» — яйца и
  сковорода в холодильнике, тарелки в навесном шкафу, корзина в тумбе,
  графин в кофемашине. В режиме стройки те же предметы выделяются (там своя
  система выбора, гейты интерактива не спрашиваются).
- **Причина:** правило `Interactor.ThroughOpening` (добавлено в тот же день
  под задачу «яйцо не кликается сквозь борт кастрюли») требовало, чтобы луч
  вошёл в хозяина СВЕРХУ (`hostHit.normal.y >= 0.4`). В шкаф смотрят СБОКУ
  через открытую дверцу — подмена «вложенный побеждает хозяина» не
  срабатывала, наведение оставалось на корпусе.
- **Как решили:** `ThroughOpening(hostHit, nearest, host)` получил третьим
  параметром хозяина и сразу отвечает «да», если у его дефа есть `slotNodes` —
  содержимое лежит НА ПОЛКАХ за дверцей (холодильник, навесной шкаф, тумба,
  кофемашина). Для посуды без слотов (кастрюля, сковорода) правило работает
  как было: сквозь борт не кликается, сверху — да. Гейт по открытой дверце не
  нужен: закрытые секции отсекает `HoldsClosed` в `SkipHit`. Проверено замером
  ilya-71: тарелка в шкафу — с трёх ракурсов, яйцо в кастрюле сквозь борт —
  нет.
- **Продолжение (тот же вечер):** исключение по `slotNodes` оказалось слишком
  широким — в осмотре кофемашины наведение на КРЫШКУ выделяло бак за ней
  (Илья: «навожу на крышку, а выделяется бак»). Итоговое правило в
  `ThroughOpening` из трёх шагов: (1) луч упёрся в деталь хозяина
  (`io.IsPart` — крышка, дверца, стенка) ⇒ содержимое НЕ выигрывает;
  (2) у хозяина есть `slotNodes` ⇒ видно через проём с любого ракурса;
  (3) иначе посуда — только сверху в горловину.
- **Правило на будущее:** ограничение «откуда виден предмет» проверять на
  ТРЁХ случаях — посуда с горловиной, мебель с открытой дверцей и сплошная
  деталь хозяина перед содержимым; различают их `IsPart` и `slotNodes`.
- **Диагностика (что сработало):** объект внутри контейнера проверяется по
  цепочке — `Container`, `HoldsClosed`, `SkipHit` по каждому коллайдеру,
  переполнение буфера лучей, покрытие точки экраном UI. Всё было чисто, и
  виновника нашёл `git diff` по рабочему дереву: единственная строка, которая
  меняла подмену вложенного. ⭐ На общем дереве СНАЧАЛА смотри diff чужих
  правок за день, а потом рой в своей логике.
- **Грабля зонда (ilya-71):** камера пробы может встать ЗА СТЕНОЙ — первым в
  луче окажется кусок стены, и замер покажет «ничего не выделяется» там, где
  в игре всё работает. Ракурс считать от объекта, со стороны комнаты.

### Обводки стирали друг друга общим битом трафарета (2026-08-30, ilya-42)

- **Симптом:** выделенная плита и наведённая рядом тумба сливались в ОДИН
  контур без границы между ними (скрин 23:50); предмет, стоящий на выделенной
  тумбе, «не выделялся вовсе» — хотя кликался и подсветка ему включалась.
- **Причина:** маска силуэта (`InteractOutlineMask`) писала бит 1, а кант
  (`InteractOutline`) рисовался там, где `(стенсил & 33) == 0`. Бит один на
  всех: маска ЛЮБОЙ горящей обводки гасила кант соседней, а маска большого
  объекта — кант всего, что стоит внутри его силуэта на экране.
- **Как решили:** бит стал свойством материала (`_StencilBit` у маски,
  `_StencilRead` у канта). `InteractHighlight` держит наборы материалов на
  пять битов (1, 2, 4, 8, 16; бит 32 по-прежнему рентген персонажа) и выдаёт
  свободный бит обводке НА ВРЕМЯ ПОКАЗА (`OnEnable`), освобождая в
  `OnDisable`. Одновременно горящие обводки больше не пересекаются.
- **Правило:** любой эффект на стенсиле в этой игре обязан объявлять СВОЙ бит
  и маску чтения; общий бит «на всех» ломается, как только объектов больше
  одного. Проверять сценарием «выделен один объект, наведён другой рядом».

### Декоративный HUD глушил наведение на мир (2026-08-30, ilya-42)

- **Симптом:** «навожу на предмет — не выделяется», причём в режиме стройки
  тот же предмет выделяется. Повторялось для вещей, которые на экране
  оказались под верхней панелью или под шкалами состояния.
- **Причина:** `Interactor.Update` целиком выходит, если `UiPointer.OverUI()`,
  а тот отвечает «да» на ЛЮБОЙ графике интерфейса под курсором — включая
  фон верхнего бара и полоски здоровья. В стройке своя система выбора, она
  этот гейт не спрашивает — отсюда разное поведение.
- **Правило:** декоративная графика HUD (баров, шкал, подписей, чипов) должна
  иметь `raycastTarget = false` — общий помощник `UiFactory.PassThrough(root)`
  снимает его со всего поддерева, кроме кнопок (`Selectable`). Блокировать
  курсор имеют право только настоящие панели и модалки.

- **Не забыть:** новый рантайм-шейдер (`Shader.Find`) — сразу в Always
  Included Shaders через редакторский API, иначе в сборке будет розовый.

## Предмет пропадал совсем вместо красного (2026-08-31, ilya-71)

Три независимые причины у одного симптома. Илья: «сковородка стала пропадать
совсем иногда при перемещении её на другие объекты, хотя должна становиться
красной, и пропадает при наведении под воду».

- **Причина 1 — «подготовка глубины» писала мусор.** В `Cozy/SolidOverlay`
  проход DepthPrime шёл с `ZTest Always` + `ZWrite On` и клал СВОЮ глубину.
  При `ZTest Always` в буфер побеждает ПОСЛЕДНИЙ нарисованный фрагмент, а не
  ближний, то есть глубина получалась от случайного треугольника, и второй
  проход с `ZTest LEqual` зависел от порядка вершин в модели и угла камеры.
  **Правило:** проход подготовки должен ГЛУБИНУ СТИРАТЬ, а не писать свою:
  `clip.z = 0` при `UNITY_REVERSED_Z`, иначе `clip.z = clip.w` — дальняя
  плоскость в силуэте. Самозаслонение честно получится во втором проходе.
- **Причина 2 — вложенные предметы в ОДНОЙ очереди с хозяином.** Посуда и её
  содержимое стояли обе на 4200, а порядок внутри очереди решает сортировка по
  расстоянию до центра — у сковороды и лежащих в ней яиц центры почти
  совпадают, поэтому порядок скакал от кадра к кадру: то яйца тонули под
  сковородой, то сковорода под яйцами. **Правило:** хозяин и содержимое —
  РАЗНЫЕ очереди (4200 и `ContentsQueue` 4300), а не одна.
- **Причина 3 — статический кэш материала поверх незагруженного шейдера.**
  `HandBlockedMat` создаётся один раз на домен-сессию. Если в момент первого
  обращения `Shader.Find` вернул null, материал НАВСЕГДА оставался без шейдера
  и не рисовал ничего — до перезахода, отсюда «иногда». **Правило:** материал
  на рантайм-шейдере не кэшировать, пока шейдер не найден; на этот случай
  держать откат на обычный материал.
- **Общее:** «иногда пропадает» почти никогда не одна причина. Симптом
  «объект не нарисовался» разбирать по трём слоям сразу — глубина, очередь,
  материал.

## Предмет на полке дверцы не выделяется (2026-08-31, ilya-1c)

**Симптом (Илья):** «я почему-то не могу выделить объекты масла, кетчупа и
газировки» — бутылки стоят на полке ОТКРЫТОЙ дверцы холодильника, наведение
упорно отдаёт сам холодильник, карточка бутылки не открывается.

**Ложные следы, которые проверены и отпали** (чтобы не ходить туда снова):
объекты живые и кликабельные (`DefClickable` = true, коллайдеры включены,
`activeSelf` = true); слот дверцы ОТКРЫТ (`ContainerSlot.HoldsClosed` = false,
`Slot_DoorB.Open` = true); правило «продукт выделяется только в осмотре прибора»
ни при чём — у бутылок `isProduct` = false. Всё это снято дампом из живой игры
через MCP, а не чтением кода.

**Причина:** `Interactor.ThroughOpening` рубит вложенное, если луч попал в
СПЛОШНУЮ ДЕТАЛЬ хозяина (`io.IsPart(hostHit.collider.transform)`). Правило
завели, чтобы крышка кофемашины не отдавала бак за собой. Но полка дверцы —
тоже деталь, и всё, что на ней СТОИТ, попадало под тот же запрет: луч упирался
в полку, вложенное проигрывало, выигрывал холодильник.

**Починка:** различать «за деталью» и «НА детали». В `ThroughOpening` теперь
передаётся коллайдер ВЛОЖЕННОГО (`nestedCol`, раньше по ошибке шёл коллайдер
хозяина), и запрет не срабатывает, если вложенное — потомок этой детали:
`!nested.transform.IsChildOf(hostHit.collider.transform)`. Бутылки на полке
выделяются, бак за крышкой кофемашины по-прежнему нет.

⭐ **Правило:** появилась «сплошная деталь» — сразу спроси, может ли на ней
что-то СТОЯТЬ. Полка, столешница, откинутая дверца — это опора, а не преграда,
и содержимое на них должно оставаться доступным.

  `digits.forward = (0,0,−1)` ⇒ ровно наоборот.
- **Правило:** мировую надпись/эффект на месте узла-пустышки ориентируем по
  РОДИТЕЛЬСКОМУ узлу с мешем (у панели: наружу `panel.up`, вертикаль
  `-panel.forward`), а не по повороту самой пустышки. Проверка одна: знак
  смещения выпуклой детали (клавиши) от плитки по тонкой оси.

## Надпись на модели читается зеркально (2026-08-31, ilya-71)

- **Симптом:** на панели холодильника «+3» и «-8» выглядели как «e+» и «8-».
  Илья: «тексты на холодильнике будто перевёрнуты».
- **Причина:** мировой текст строился по оси НОДЫ модели
  (`Quaternion.LookRotation(panel.up, …)`), а знак этой оси зависит от того,
  как объект развернули при экспорте. Ось смотрела ВНУТРЬ дверцы, текст был
  повёрнут лицом в плитку, и игрок видел его изнанку — TMP рисует букву с двух
  сторон, поэтому надпись не пропала, а отразилась.
- **Правило:** направление «наружу» у надписи на модели НЕ брать у ноды на

  несовпадении менять знак. Вертикаль так же приводить к мировому верху.
  Это же касается сдвига надписи от поверхности: с неверным знаком она
  утапливается внутрь вместо того, чтобы выступать.
- **Как ловить:** замерить в play `text.transform.forward` и направление от
  надписи к камере — если скалярное произведение отрицательное, игрок смотрит
  на изнанку.

## Обход граней: Blender двусторонний, URP — нет (2026-08-31, ilya-42)

- **Симптом:** пятно на фильтре кофемашины было включено, покрашено правильно,
  `isVisible=True`, габарит на месте — и не рисовалось в игре, хотя в
  блендер-превью выглядело как надо (Илья: «фильтр не меняет визуал при
  загрязнении»).
- **Причина:** материал в Blender по умолчанию ДВУСТОРОННИЙ, а URP/Lit
  отсекает изнанку. Полоса пятна строилась обходом «наружу», и в воронке, куда
  смотрят СВЕРХУ-ВНУТРЬ, от неё оставалась только невидимая изнанка.
- **Правило:** для накладок, которые смотрят внутрь чаши/воронки, обход граней
  задавать нормалью К ОСИ. Проверка без запуска игры: инстанс модели в edit
  mode, средняя `dot(normal, radial)` по вершинам — минус для «смотрит внутрь»,
  плюс для «наружу» (`ConeWet`/`MachineWet` ≈ −0.75, `GroundsWet` ≈ +0.57).
- ⚠️ **Ось в импортированном меше — не Y.** Вершины FBX приходят в блендеровской
  системе (ось конуса = Z, радиус в плоскости XY), разворот живёт в трансформе
  узла. Первый замер я сделал в плоскости XZ, получил бессмысленные числа и
  развернул обход НЕ в ту сторону. Прежде чем считать радиальную компоненту —
  смотреть `mesh.bounds.size`: тонкая ось и есть ось модели.

## Двойной клик по мелкой детали не срабатывает: её перекрывает бокс объекта

**Симптом.** Настенный выключатель не переключался двойным кликом вне
выделения, хотя `useAnywhere` стоял и `IsPart(Key)` возвращал true
(Илья 2026-08-31).

**Причина.** `Interactor` выбирает деталь по правилу «часть побеждает, если её
попадание не дальше ближайшего более чем на `PartTie` = 1 см». Общий бокс
объекта строится по следу дефа и торчал перед клавишей: замер лучом дал корпус
на 1.172 и клавишу на 1.182 при наклоне 55° — ровно на границе допуска, поэтому
клик срабатывал через раз.

**Правило.** У объекта, чья интерактивная деталь выступает вперёд, физический
бокс задавать `colliderNode` по КОРПУСУ (у выключателя — `"Plate"`), а не
следом. Тогда триггер детали ловит луч первым с запасом 2–4 см под любым углом
камеры. Проверка — `Physics.RaycastAll` из точки перед деталью под углами
0/35/55°: первым в списке должна идти деталь.

## Луч попадает в ЕДУ, а действие адресовано ПРИБОРУ (2026-08-31, ilya-1c)

**Симптом.** Кетчуп над полной тарелкой не даёт ни блюпринта, ни действия:
над пустым прибором похожие жесты (масло, губка) работают.

**Причина.** `ServeTargetUnder` возвращает БЛИЖАЙШИЙ объект по лучу. У блюда
с едой ближайшим всегда оказывается порция (яйцо/сосиска), а вложенный
приёмник берётся только если он сам `Receives` — у продукта раскладок нет.
Дальше `SaucesWith(егоDef, кетчуп)` ложно, и предложение не рождается.

**Правило.** Действие, которое ПО СМЫСЛУ адресовано прибору с содержимым
(полить соусом, посыпать, подать), ищет цель ещё и у хозяина порции:
`io` → `io.Container`. Смазка и мойка этим не страдали только потому, что
применяются к пустому прибору.

## Процедурный веер смотрит нормалями ВНИЗ (2026-08-31, ilya-1c)

**Симптом.** Кетчуп «не наливается»: ни лужицы, ни блюпринта. В сейве при
этом видно, что из бутылки ушло 30 мл — то есть действие СРАБАТЫВАЛО, просто
результата не видно.

**Причина.** Меш лужицы строился веером `(0, i+1, i+2)` по возрастанию угла в
плоскости XZ. В Unity лицевая грань — по ЧАСОВОЙ при взгляде с лицевой
стороны, и такой обход даёт нормаль вниз: лужицу видно только из-под тарелки,
URP заднюю грань не рисует.

**Правило.** У любого процедурного диска/веера в XZ обход идёт `(0, i+2, i+1)`.
Проверка на бумаге: нормаль = cross(b−a, c−a), её `y` должен быть > 0.
И симптом на будущее: «действие не работает» + расход ресурса в сейве =
не логика, а невидимая геометрия.

### Метровый куб вместо канта по форме

  рендерер; иначе преобразование запекается. Задевает любую деталь, где меш

### Флаг-ворота убил рычаги (повтор темы «тест описал не весь смысл»)

- **Симптом:** «двойные клики по рычагам перестали работать для раковины и

- **Причина:** ночной тест требовал у «используемого глобально» объекта
  створки, и по нему я снял `useAnywhere` с мойки и стояка — у них дверец нет,

  объявившая глобальность на себе. И перед «чисткой лишнего флага» по тесту
  грепать, кто его читает.

### Клавиша, которую нельзя нажать

- **Симптом:** «я описывал логику, что выключатель включает светящиеся

- **Правило:** если единственный орган управления — часть, у неё обязан быть
  способ нажатия: либо осмотр у дефа, либо `useAnywhere` на самой части.

### Предмет ложился внутрь закрытой тумбы

## Снесённый рендерер ломает габарит объекта — и предметы проваливаются

**Симптом.** Предмет, поставленный на полку холодильника, проваливался вниз
сквозь полку; заодно снова пропали цифры температуры на табло
(Илья 2026-08-31).

**Причина.** `ChamberTempLabel` сносил рендер запечённой заглушки
(`Destroy(r)`), а `InteractiveObject._renderers` — массив, собранный при
постройке модели. В нём оставалась ссылка на убитый компонент, и `WorldBounds`
падал с `MissingReferenceException`. Дальше рушилось всё, что считает опору и
габарит: постановка на полку и `Update` самой надписи (она читает
`io.Working`).

**Правило.** У объекта с кэшем рендереров компоненты НЕ сносить. Спрятать
запечённую деталь — `forceRenderingOff = true` (плюс `enabled = false`):
гейты видимости трогают только `enabled`, а `forceRenderingOff` держится и
ссылка остаётся живой. Если сносить всё же приходится — чистить кэш
(`_renderers`) в том же кадре.

**Как ловить.** Исключение видно не в консоли игры, а по симптому «физика/
постановка сошла с ума у ОДНОГО объекта»: пройтись `WorldBounds` по
`InteractiveObject.All` из execute_code — падение укажет виновника сразу.

## Кант обводки не поехал за деталью (2026-09-01, ilya-1c)

**Симптом.** Рычаг крана поднят, а обводка обрисовывает его В ОПУЩЕННОМ
положении: силуэт «отстаёт» от детали.

**Причина.** Обводка объединяет меши ПО ВЕТКАМ и печёт объединённый меш один
раз. Ветками считаются только узлы из списка `moving` — там были створки и
ящики, но не ТУМБЛЕРЫ. Меш рычага попадал в общий кузов и застывал в позе,
какая была при первой подсветке.

**Правило.** Любой узел, который двигает код (`ObjectSwitch.node`, ведомая
`linkNode`, створка, ящик), обязан быть в `MovingParts()` — иначе его силуэт
остаётся в старой позе. Симптом на будущее: «обводка не совпадает с деталью»
= деталь не объявлена подвижной.

## Повторяющийся класс: подвижная часть проходит СКВОЗЬ свой же объект

**Симптом (ловится не первый раз, Илья 2026-09-01).** Дверца углового
навесного шкафа при открывании уезжала в короб соседнего плеча; вторая створка
проходила сквозь уже открытую первую.

**Причина.** Ограничитель хода (`OpenLimit`/`CollectPartHits`) пропускал ВСЕ

Правило задумывалось как «дверца не должна цепляться за собственный корпус», но
для этого уже есть отдельный механизм — набор `_partTouching`, куда попадает
всё, чего часть касается В ЗАКРЫТОМ положении.

**Правило.** Пропускать в ограничителе только САМУ подвижную часть
(`IsChildOf(m.tf)`) и содержимое (`io.Container == this`). Тогда створка
упирается и в свой корпус, и в соседнюю створку того же объекта, а постоянные
касания по-прежнему не мешают.

**Вторая половина той же баги (Илья 2026-09-01, повторная жалоба).** Даже
после этого створки проходили друг сквозь друга, включая соседние шкафы:
коллайдер подвижной части — ТРИГГЕРНЫЙ (`AttachPartCollider`), а запрос помех
шёл с `QueryTriggerInteraction.Ignore`, то есть дверцы физически не видели одна
другую. Теперь запрос идёт с `Collide`, а чужие НЕ-частевые триггеры (зоны
наведения, площадки слотов) отсеиваются проверкой `io.IsPart(col.transform)`.

**Проверка.** Открыть обе дверцы объекта по очереди И открыть дверцу соседнего
шкафа навстречу: обе должны останавливаться, а не проходить сквозь.

## Прилипший к гнезду объект НЕ проверяется на пересечения

**Симптом.** Под один шкаф вставали ДВЕ подсветки в одно и то же место, в
списке приборов появлялись два объекта на одной точке (Илья 2026-09-01).

**Причина.** В `ValidatePose` ветка host-snap («часть судится хозяином») ставит
вердикт только по досягаемости руки и делает ранний выход — общая проверка
пересечений до неё не доходит. Это правильно для бака в нише (он ОБЯЗАН
пересекать корпус), но означает, что занятость самого гнезда никто не проверял.

**Правило.** В этой ветке добавлять проверку занятости точки посадки
(`MountTaken`, радиус 20 см, считаются объекты со `snapToId`). Общую проверку
пересечений включать обратно НЕЛЬЗЯ — сломает установку в ниши.

## Прилипание боком уводит объект в стену: взята ЧУЖАЯ глубина

**Симптом.** Прямой навесной шкаф прилип к боку углового и встал внутрь стены
(Илья 2026-09-01). До этого он же не липнул к угловому вовсе.

**Причина, найденная замером.** Порядок в расчёте позы: `SnapToWall` (посадка
спиной к стене по СВОЕЙ глубине) → `SnapKitLine` (прилипание к соседу).
Прилипание переписывало X/Z целиком, вычисляя точку от центра соседа. Пока
соседи одинаковой глубины, разницы нет; угловой шкаф глубже прямого (1.52
против 0.6), и прямой уезжал по глубине. Выравнивание СПИН вместо центров тоже
не лечит: у углового с разных сторон разная глубина — вдоль главного плеча 0.69,
вдоль крыла другая, и с одной стороны ошибка меняет знак.

**Правило.** От соседа при боковом прилипании берутся ТОЛЬКО боковое смещение,
высота и разворот. Глубина остаётся своя — её уже посадил `SeatBackToWall`.
В коде: спроецировать разницу позиций на боковую ось соседа и сдвигаться только
вдоль неё.

**Проверка.** Прилипить прямой модуль к обоим бокам углового и померить X/Z
спин: обе спины обязаны лежать на одной плоскости стены. Замер стены —
`BuildQuery.WallLikeAt` шагом 0.2 м, он же отсекает гипотезу «перепутан знак».

**Смежное.** Липнут боком модули ОДНОГО КОМПЛЕКТА на одной высоте стены
(`WallKitMate`), а не только одинаковые дефы: раньше сравнивался `def.id`, и
угловой с прямым друг друга не видели.

## Чёрные зубья по кромке детали (2026-09-01, ilya-71 → чинила ilya-1c)

- **Симптом:** по всей длине подсветки под навесным шкафом шла регулярная пила
  из чёрных треугольников; видно было только на одном плече — второе смотрело
  от камеры.
- **Причина:** СОВПАДАЮЩИЕ ГРАНИ. В `underlight_scene.py` корпус занимал по
  высоте от рассеивателя до верха профиля, а тёмная монтажная планка — верхние
  7 мм того же диапазона. Планка целиком внутри корпуса, и их верхние грани
  лежали в ОДНОЙ плоскости — спор глубины (z-fighting), который в Blender
  незаметен, а в игре даёт мерцающую пилу.
- **Правило:** деталь, лежащая НА другой, не должна делить с ней плоскость.
  Вычитай её толщину из несущего тела (`body_h = H − LENS − RAIL`), а не
  клади поверх «в тот же объём»: высота объекта остаётся прежней, силуэт тоже,
  а грани расходятся. Проверять надо в ИГРЕ и с двух сторон: на обращённом от
  камеры плече дефект не виден.
- **Смежная грабля оттуда же:** в `*_params.json` остаётся флаг варианта от
  прошлой сборки (`corner: true`), и экспортёр падает `KeyError` по корню,
  которого в сцене нет. У каждой записи реестра, где вариант выбирается
  флагом, должен стоять свой `force={...}` — иначе сборка зависит от того, кто
  последним крутил GUI.

## Плечо Г-образной детали меряется ОТ ЛОКТЯ (2026-09-01, ilya-71 → поймала ilya-1c)

- **Что я сделал не так:** увидел, что у углового шкафа участки подвеса равны
  1.21 и 0.90, а плечи угловой лампы — 1.14 и 1.44, счёл это расхождением и
  «починил», поставив плечам длины участков. Стало ХУЖЕ: одно плечо вылезло за
  корпус, второе не дошло. Правка откачена, вернулись 1.14 / 1.44.
- **Причина:** числа из РАЗНЫХ систем отсчёта. Масштаб узла подвеса — это длина
  участка ШКАФА, то есть длина прямой лампы, которая висела бы под этим плечом.
  А плечо Г-образной лампы меряется ОТ ЛОКТЯ до дальнего края корпуса: локоть
  на (−0.54, 0.69), корпус x[−0.60, 0.60] z[−0.75, 0.75], отсюда 0.60−(−0.54) =
  1.14 и 0.69−(−0.75) = 1.44.
- **Правило:** прежде чем объявлять два числа расхождением, убедись, что они
  меряются ОТ ОДНОЙ ТОЧКИ. У составной детали (уголок, тавр, П-образная рама)
  длина плеча — это вылет от узла стыка, а не габарит соседа, к которому она
  крепится. Арифметику писать в комментарий рядом с узлом: «угол + плечи = ровно
  габарит корпуса» — так проверка занимает секунду и не требует игры.
- **Что в этой истории всё-таки верно:** числа, от которых зависит стыковка с
  другим объектом (длина плеча, шаг гнёзд, вылет, толщина под врезку), обязаны
  лежать в `<x>_params.json` ЯВНО, а не в умолчаниях кода сцены — у угловой
  лампы ключей `corner_a`/`corner_b` не было вовсе, и посмотреть на настоящие
  значения было негде. Ключи оставлены явными и после отката.
- **Смежное (ilya-1c, тот же день):** в params, наоборот, залипает флаг варианта
  от прошлой ручной сборки (`corner: true`), и экспортёр падает по
  отсутствующему корню. Params задают ЧИСЛА, реестр через `force={...}` задаёт
  ВАРИАНТ.

## Радиус «по коробке» вместо «по телу» разносит объекты (2026-09-01, ilya-42)

- **Симптом:** «кружка далеко от тарелки, надо ближе» — пара блюда стояла с
  просветом в 5 см даже после того, как убрали нахлёст.
- **Причина:** радиус для пары брали как половину габаритного бокса, а бокс
  кружки шире тела на ручку. Пара разъезжалась на длину ручки, даже когда та
  смотрит в сторону.
- **Правило:** для «встать рядом» мерить радиус от СОБСТВЕННОГО центра предмета
  до ближней стенки бокса — у объекта с выступом центр остаётся в теле, а
  выступ уводит только дальнюю грань. Нижний предел (60 % от половины бокса)
  страхует модели с пивотом не в центре.

## Карточка связки цеплялась за кликнутый предмет (2026-09-01, ilya-42)

- **Симптом:** «у объединённого объекта UI у объекта, по которому кликнул, а
  должен быть справа от крайнего».
- **Причина:** мировая панель считает силуэт по ОДНОМУ объекту — тому, что
  выбран. У связки участников несколько.
- **Правило:** силуэт для панели считается по всей связке
  (`SilhouetteRect.Collect(root, extra)`); у любой групповой сущности якорь UI —
  габарит группы, а не её участника.
