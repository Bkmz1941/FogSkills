# Приёмы рефакторинга — что применяем в этом проекте

Собрано из практики проекта и из общепринятых источников (Фаулер «Refactoring»,
Физерс «Working Effectively with Legacy Code», метод Микадо, strangler fig),
переведено на наши условия: Unity 6.3, C#, пять параллельных сессий, живая игра
без автотестов на геймплей.

## 1. Как выбирать цель

Порядок вопросов, а не список красивых идей:

1. **Что болит?** Цель берётся из боли: место, где сессии регулярно ошибаются,
   где баги повторяются (`bugs.py <область>` покажет плотность), где правка
   одной механики ломает соседнюю. Красивый, но спокойный код не трогаем.
2. **Есть ли защита?** Смотрим `tavern-regress/COVERAGE.md`. Нет защиты —
   первым шагом делаем её, а не правку.
3. **Обратим ли шаг?** Если откат стоит дороже правки, цель дробится дальше.
4. **Влезает ли в один зелёный шаг?** Цель, которую нельзя довести до
   компиляции и зелёных тестов за один заход, разбивается методом Микадо (§4).

Приоритет между целями: **риск повторного бага > стоимость чтения > красота.**

## 2. Характеризующий замер (наш аналог characterization test)

У геймплея нет юнит-тестов, и написать их на MonoBehaviour дорого. Заменяем
замером: перед правкой снимаем с ЖИВОЙ игры числа, которые обязаны сохраниться.

Как: `execute_code` через мост, `FindObjectsByType` + счётчики, координаты,
состояния флагов. Печатаем одной строкой, кладём в отчёт шага. После правки —
тот же вызов, посимвольная сверка.

Что мерить:
- количество объектов области и их позиции (постановка, перенос);
- значения ViewState на характерных точках (видимость);
- результат `LevelIO.Save` → `Load` (круговой сейв, `level_roundtrip.py`);
- счётчики рендереров/материалов (визуальные правки).

Замер фиксирует ФАКТИЧЕСКОЕ поведение, включая странное. Если замер показал
странность — это находка для `PITFALLS.md`, а не повод «заодно починить»:
починка поведения не является рефакторингом и идёт отдельным шагом.

## 3. Швы: как разорвать зависимость, не ломая

Шов (Физерс) — место, где поведение можно подменить, не правя код в этом месте.
Наши швы, по возрастанию цены:

| Шов | Когда | Цена |
|---|---|---|
| Статический флаг (`ViewState.*`) | включить/выключить новую ветку целиком | дёшево, но флаг надо потом убрать |
| Отдельный компонент на том же GameObject | вынести визуал или побочный эффект | дёшево, ordering-безопасно, если владелец зовёт `Sync()` сам |
| `partial`-файл | разложить god-object по темам БЕЗ смены типа | бесплатно, но не уменьшает связность |
| Новый класс + делегирование | вынести настоящую ответственность | дорого, требует переноса состояния |
| Интерфейс + подмена | только если правда нужны две реализации | дороже всего, по умолчанию отвергаем |

**Правило проекта:** `partial` — это раскладка по полкам, а НЕ архитектура.
GridCursor в 35 партиалах читается лучше, чем в одном файле, но остаётся
god-object'ом на 11k строк и 176 public-членов. Настоящее разрезание — вынос
состояния в отдельный класс, и оно делается только по методу Микадо.

## 4. Метод Микадо — для целей, которые не влезают в один шаг

1. Пробуем сделать изменение «в лоб».
2. Компилируем. Сломалось — записываем, ЧТО сломалось (это предусловия).
3. **Откатываем правку целиком** (`git checkout`), не чиним по месту.
4. Берём одно предусловие и делаем его отдельным зелёным шагом с коммитом.
5. Повторяем, пока исходное изменение не станет тривиальным.

Ключевое, что все нарушают: шаг 3. Чинить по ходу — значит собрать пачку
несвязанных правок, которую нельзя ни проверить, ни откатить.

## 5. Strangler fig — замена подсистемы на живой игре

Новое рядом со старым, переключатель, перенос потребителей по одному, снос
старого последним шагом. У нас это буквально `ViewState.HiddenRooms`: весь
новый режим живёт под флагом, при выключенном флаге игра бит-в-бит прежняя.
Так же снесли темноту 13.08 — но там сначала снесли, а потом строили, и это
стоило недели. **Сначала флаг, потом код, снос — последним.**

## 6. Каталог мелких приёмов (наши, проверенные)

- **Правило трёх.** Два похожих куска не трогаем. Третий — выносим. Раньше
  третьего вынос почти всегда даёт неправильную абстракцию.
- **Общие примитивы — брать, а не писать.** Луч, сетка, габариты, силуэт уже
  есть (`ARCHITECTURE.md`, «Общие примитивы»). Новый локальный хелпер, дублирующий
  примитив, — сам по себе дефект.
- **Один писатель на поле.** У `renderer.enabled` один писатель — FloorPieceView;
  у ViewState — ViewSensor. Появился второй — это баг, а не стиль.
- **Одна формула на один вопрос.** Вопрос «что режет комнату» имеет ровно один
  ответ в коде (`ViewSensor.WallBetween`/`OpeningKindBetween`). Понадобилась та же
  формула в другом месте — делаем существующую `public`, а не пишем вторую.
- **Метод длиннее ~60 строк** — кандидат на разбиение, но только если у него
  видны СМЫСЛОВЫЕ части. Резать по счётчику строк запрещено.
- **Никаких комментариев** (правило 7 `tavern-game/SKILL.md`): тянет пояснить —
  переименуй или вынеси в метод с говорящим именем.
- **Мёртвый код удаляем только с доказательством**: поиск по всей базе, включая
  строковые имена (`Resources.Load`, `Invoke`, `SendMessage`) и сцены. Публичный
  член без потребителей может звать редактор или сейв.

## 7. Чего в этом проекте делать НЕ надо

Проверено практикой и отвергнуто:

- **DI-контейнеры и слои абстракции «на будущее».** Проект соло-разработчика,
  правило простоты — закон. Отвергаем по умолчанию.
- **Интерфейс ради одной реализации.** Пока реализация одна, интерфейс только
  добавляет прыжок при чтении.
- **Резать god-object «на классы» одним заходом.** GridCursor пытались резать
  несколько раз; выжила только раскладка по партиалам и вынос НАСТОЯЩИХ
  подсистем (ViewSensor — единственный писатель ViewState).
- **Централизованный update-manager.** У нас уже есть `TickAll` там, где это
  окупалось (FloorPieceView, PlacedFloorView — сотни экземпляров). Расширять
  приём на всё подряд не нужно.
- **Массовое переименование.** Ломает поиск по журналам и граблям, где имена
  зафиксированы навсегда.

## 8. Чем доказывать результат

Рефакторинг без числа — это мнение. Каждый закрытый пункт `TARGETS.md` несёт:

- замер ДО и ПОСЛЕ (см. §2) — одинаковые;
- `check_all.py` зелёный;
- метрику улучшения: строк стало меньше на N, дублирование ушло из M мест,
  публичная поверхность класса уменьшилась на K членов, мусор на кадр упал
  на X КБ (`gc_probe.py`).

Если метрику назвать нечем — цель была не рефакторингом, а вкусовщиной.

## Источники

- Фаулер, «Refactoring»: правило трёх, каталог запахов, «рефакторить только то,
  что собираешься менять».
- Физерс, «Working Effectively with Legacy Code»: швы, характеризующие тесты,
  порядок «точка изменения → точка теста → разрыв зависимости → тест → правка».
- Метод Микадо (Элльнестам, Брулунд): откат и граф предусловий.
- Strangler fig (Фаулер): постепенная замена подсистемы под переключателем.
