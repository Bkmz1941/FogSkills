## ⭐ Железные правила Ильи — нарушение каждого уже стоило времени

1. **Сначала ТОЛЬКО Blender, Unity потом.** Никакого экспорта, пока Илья не
   сказал «отлично / норм / переноси» на форму в открытом окне.
2. **Правки смотрим в ОТКРЫТОМ файле, а не скринами** (04.09). Окно открыто,
   сцена пересобирается сама по сохранению, смотрит человек. Своё состояние
   сессия читает МОСТОМ (число объектов, материалы, габариты), а не картинками.
3. **Кадры Илье не шлём вообще** (05.09: «не делай png никогда для меня»).
   Смотреть рендер для СВОЕЙ проверки можно, отдавать — словами и цифрами.
4. **Один объект — один `.blend`** (03.09). Истина по форме — `<x>_scene.py`;
   сборка пишет один `Library/<модельUnity>.blend`. Рабочих копий `*_work.blend`
   не держим. Комбинация — только с явным `_combo`/`_combos` в имени.
   ⚠️ Живое нарушение на сегодня: `BlenderWork/tree_work.blend` в корне — так
   не делаем, файл регенерируется запуском сцены.
5. **Новых файлов без просьбы не заводим** (03.09). У темы ОДИН рабочий файл;
   «отдельную сцену чтобы посмотреть» не создаём и окно на неё не переключаем.
6. **Правка идёт в ЭТАЛОН и переэкспорт**, никогда — подкруткой ассета в Unity.
   Расхождение «в игре выглядит иначе» лечится приведением игры к эталону.
7. **Блендер-модель — эталон по форме И по текстуре.** Текстуры, пришедшие из
   Blender, в Unity не переделываем.
8. **Мерка — ПЕРСОНАЖ (2.55 м), а не реальный мир.** Опорные высоты по костям:
   носок 2.6 см, щиколотка 15, бедро 125, низ живота 136, локоть 159, голова 207.
9. **Палитра — из `KenneyStyle.cs`,** свои тона не выдумываем; сомневаешься —
   рендерь 2–3 варианта контактным листом и показывай Илье.
10. **Ориентацию и цвет МЕРЯТЬ, а не выводить.** Blender→Unity здесь отражение
    `(bx,by,bz) → (−bx, bz, −by)`, определитель −1: рассуждение систематически
    врёт, а картинка при этом выглядит правильной.
11. **Гладкость — НОРМАЛЯМИ, а не плотностью сетки** (18.09, раковина). «Оч
    угловато» лечится гладкими нормалями при той же сетке, а не удвоением
    сегментов: 32 сегмента с гладкими нормалями читаются круглее, чем 48
    плоских, и вдвое дешевле. Кит всегда отдаёт ПЛОСКИЕ нормали (`_finish` →
    `flat`), поэтому гладкость навешивает сцена: бочок цилиндра гладкий при
    плоских торцах (`abs(poly.normal.z) < 0.5`), у фаски куба — все полигоны
    гладкие плюс `harden_normals` на модификаторе (плоские грани остаются
    плоскими, круглится только фаска), у тела вращения — `use_smooth` по
    всем полигонам. Мерка веса — СЕМЬЯ объекта: унитаз и ванна по ~1400
    треугольников, раковина с ящиками и смесителем 2048 (2944 при тумбе
    2.0, ужата до 1.5 × 1.0 19.09); вышел в разы за
    соседей — сначала убавь сетку, а не бюджет.
12. **Ровный объект — брак, асимметрия обязательна** (Илья 11.09, яблоко:
    «сделай не идеальным, без симметрии»). Правило было записано только для
    мягких вещей — теперь оно общее и для органики: ровное тело вращения не
    отдаём. Минимум — дольки по окружности, одна щека полнее другой, волна
    радиуса по высоте, 3–4 гауссовы вмятины и наклон верха, всё от сида.
    Вмятины давить ПО РАДИУСУ, а не по нормали, иначе опорное кольцо уходит
    с z=0 и предмет висит над столом. Варианты цвета — РАЗНЫЕ сиды, иначе это
    перекрашенная копия, а не второй предмет. Эталон — `apple_scene.py`.
13. **Объект НЕ входит в стену** (Илья 20.09, пылесос «прям в стене»). В
    сцене с контекстной стеной самая задняя точка геометрии лежит НА плоскости
    стены (в `bedroom_tech` — `WALL_Z`), ни одного полигона за ней; у навесных
    спинка касается стены, не тонет в ней. Проверяется числом, а не глазом:
    `seat_back(root, WALL_Z)` из кита двигает объект так, что max z мешей =
    стене (образец — пылесос в `bedroom_tech_scene.py`), а зазоры до стены
    задаются геометрией, не координатами «на глаз». Собрал объект у стены —
    сверь max z по мешам с z стены ДО показа Илье (P488).

## Два пайплайна, и их не надо путать

Это главная развилка при заведении новой сцены. В `BlenderWork/` живут ДВА
разных способа работы, у них разные файлы, разный экспорт и разные правила.

| | **Реестровый** — объекты | **Одиночная сцена** — стихии |
|---|---|---|
| Что так делается | мебель, еда, посуда, одежда, растительность (73 записи) | огонь, туман, дождь, ветер |
| Истина | `<x>_scene.py` + запись в `pipeline.py` | один файл `<x>3d_scene.py`, вне реестра |
| Параметры | `<x>_params.json`, ключ `<X>_PARAMS` | константы в самом файле |
| Обёртки | `build_<x>.py` / `<x>_watch.py` / `<x>_preview.py` по 2 строки | своего нет, превью внутри сцены (`FIRE3D_RENDER=1`) |
| Что уезжает в игру | FBX + `<x>-materials.json` в `Assets/Game/Resources/<Kit>/` | у тумана — банк FBX + json раскладки; у огня и ветра — ничего, геометрия в C# |
| `.blend` | `Library/<модель>.blend` от сборки | нет |
| Варианты | `numbered('tree')`, сиды в params, суффикс id в игре | варианты внутри файла, игра выбирает по координате клетки |

⭐ **`build=False` — как одна сцена берёт геометрию другой.** Сцена, которой
нужен чужой объект (миска для фруктов — яблоки внутрь, ради проверки размера),
зовёт чужую сцену через `exec` с `{'<X>_PARAMS': {'build': False}}`: та ТОЛЬКО
определяет свои функции и не делает ни `wipe()`, ни сборки. Так контекст не
копирует чужую форму и не может её разойтись. Правка формы идёт в свой файл.
Контекстные объекты держим ВНЕ корня записи, тогда в FBX они не уезжают, а
флаг показа — в `hide` реестра.

⭐ **Третий случай — ДВИЖЕНИЕ реестрового объекта** (08.09,
`tree_wind_scene.py`): анимация не форма, в FBX не уезжает и в реестр не
заводится, поэтому живёт отдельной сценой по правилам стихии. Такая сцена НЕ
копирует чужую геометрию: дерево берётся exec'ом `tree_scene.py` с одним сидом,
ленты ветра — exec'ом `wind3d_scene.py` с `WIND3D_PARAMS={'build': False}` (он
тогда определяет функции и НЕ вайпит сцену). Правка формы идёт в свой файл,
правка движения — в файл движения.

⭐ **Где живёт движение: СВОЁ — с формой, ЧУЖОЕ — отдельно.** Третий случай
выше легко прочитать как «анимация всегда отдельным файлом», и это неверно.
Разделяет не движение как таковое, а ЧЬЁ тело шевелится:

- тело двигает СЕБЯ САМО (крылья вороны, мах бабочки) — движение живёт в сцене
  самого объекта, под параметром `animate`. Разорвать их нельзя: мах — это и
  есть форма крыла во времени, а в FBX он не уедет, потому что `animate` стоит
  в `hide` и на экспорте гаснет;
- тело гнёт ВНЕШНЯЯ сила, приложенная к ЧУЖОМУ объекту (ветер по дереву) —
  движение живёт своей сценой, а форма берётся exec'ом из чужого файла.

Образцы: `crow_scene.py` и `butterfly_scene.py` — первый род, `tree_wind_scene.py`
— второй.

Стихия НЕ заводится записью в `pipeline.py` — у неё нет ни `Library/*.blend`,
ни `-materials.json`, ни `KenneyItem` в каталоге. У неё либо геометрия прямо в
C# (огонь, ветер), либо выгрузка раскладки данными (туман).

**Файлы тумана — образец полного комплекта стихии** (у неё их четыре, и это не
избыточность): `fog3d_scene.py` — сцена стихии; `fog3d_combos.py` — сцена
СОЧЕТАНИЙ на смежных клетках (как клетки стыкуются в массу); `build_fog_bank.py`
— экспортёр, пишет `Resources/Environment/fogBank.fbx` + `fogLayout.json` +
`fogBridge.json`; `fog3d_watch.py` / `fog3d_combos_watch.py` — вотчеры окон.

## Команды, которые нужны каждый раз

```bash
# Blender 5.2 LTS (с 06.10; 4.2 удалён) — `blender` в PATH: ~/.local/bin/blender → он же
/media/ilya/T714/Tools/blender-5.2.2-linux-x64

# мост Claude → Blender: поднять / открыть файл / погасить
bash BlenderWork/blender_mcp_up.sh
bash BlenderWork/blender_mcp_up.sh Library/tree.blend
# ⚠️ путь — ОТНОСИТЕЛЬНО BlenderWork/ или абсолютный: скрипт делает cd BlenderWork,
#    и `BlenderWork/Library/x.blend` удваивается в несуществующий путь — окно встаёт ПУСТЫМ (P759)
bash BlenderWork/blender_mcp_up.sh stop

# дымовой тест: строит ВСЕ объекты реестра headless, печатает tris / NOROOT / FAIL
blender -b --python BlenderWork/scene_smoke.py
blender -b --python BlenderWork/scene_smoke.py -- bed_double sponge

# GUI-Blender из фона (без DISPLAY тихо умирает)
nohup env DISPLAY=:1 blender --python BlenderWork/<x>_watch.py &

# ⚠️ второе окно, пока сосед работает: аддон моста стартует САМ в каждом окне и
# заберёт 9876 у соседа — выключать его в своём окне и сверять владельца порта
blender --python-expr "import bpy; bpy.ops.preferences.addon_disable(module='blender_mcp_addon'); bpy.context.preferences.use_preferences_save = False" \
        --python BlenderWork/<x>_scene.py
# ⚠️ use_preferences_save = False обязателен (24.09): иначе штатное закрытие
# такого окна запишет ВЫКЛЮЧЕННЫЙ аддон в настройки, и мост пропадёт у всех
ss -ltnp | grep 9876      # владельцем обязан остаться ЧУЖОЙ pid
# ⚠️ P563: настройки сохраняются при выходе — такое окно закрывать `kill -9`,
# иначе аддон моста выключится во ВСЕХ окнах; проверка после:
blender -b --python-expr "import bpy; print('blender_mcp_addon' in bpy.context.preferences.addons.keys())"
```

Помощники `blender_kit.py` (317 строк), из которых собираются сцены:
`material_factory(prefix, hex_map, rough_map)`, `srgb_to_linear`, `hex_rgb`,
`wipe`, `node`/`root`, `cube` (с chamfer), `cyl`/`pipe`/`sphere`/`limb`/`tube`/
`lathe` (круг, `section` для овала/долек или `outline` — свой план кольца, напр. `rounded_outline`), `bend_path`, `spline` (Катмулл-Ром через опорные точки — плавный путь для `tube`, шланг пылесоса 20.09; плавность пути — точками сплайна, толщина сетки — `res`, а не наоборот), `seat_back` (задняя точка мешей на стену, правило 13), `deviate`, `join` (join + `transform_apply`),
`bevel_sharp`, `rounded_outline`, `slab_bm`, `flat`, `row_start`,
`context_row`/`context_table`. Сцена делает `from blender_kit import *` и
содержит только геометрию; ей нужен `__file__` в globals.

## Чек-лист новой сцены

1. Решить, какой из двух пайплайнов (таблица выше). Стихия — одиночная сцена.
2. Файл `BlenderWork/<x>_scene.py`, идемпотентный (`wipe()` первым делом),
   параметрический, в конце `join` в один корень + `flat` + print-маркер.
3. Слежение за своим файлом, чтобы окно пересобиралось само по сохранению
   (`bpy.app.timers` + `os.path.getmtime`; в `-b` не включать).
4. Свой порт моста, если рядом работает другое окно: у огня 9877, потому что
   9876 обычно занят окном персонажа, и подключение к чужому окну уже приводило
   к чтению не той сцены. ⚠️ Порт занимает ЛЮБОЕ окно Blender, а не только
   «мостовое»: аддон включён в userpref и стартует сам. Второе окно поднимать
   с выключенным аддоном (команда выше) и проверять `ss -ltnp | grep 9876`.
   Сборка любой сцены стихии начинается с `wipe()`, поэтому попадание в чужое
   окно стирает чужую работу — P264.
5. Объект — ещё запись в `pipeline.py` (`roots` не должны пересечься с чужой
   записью: две записи с одинаковым `roots` перетирают FBX друг друга) и три
   обёртки по 2 строки.
6. Цвета: hex через `srgb_to_linear` в материалы сцены; в `-materials.json` —
   СЫРЫЕ hex/255 (sRGB). Перепутать местами — классика, растительность так
   уехала в игру темнее эталона.
7. Проверка: `scene_smoke.py`, затем сверка рендером по процедуре «перенос
   рисунка данными» — сначала ОДИН элемент, потом сцена.
7а. ⭐ ЗНАК z ХАРАКТЕРНОЙ НОДЫ В КАДРЕ ОБЪЕКТА — замер сразу после экспорта,
   ДО дефа и кнопки (P472, 18.09: зеркально уехали все четыре модели ванной).
   `go.transform.localRotation * child.localPosition`; у эталонов зад = +Z
   (`homeWallCabinet.Back` +0.285 при дверцах −0.300, `hallwayRack.Mount_Hook*`
   +0.195, кухонная мойка `RimB` +0.425). Сцена, собранная в кадре «комната =
   −z», ОБЯЗАНА звать `flip(root)` при `params['export']` — образцы
   `hallway_rack_scene.py`, `wall_cabinet_scene.py`, теперь и вся сантехника.
   Play для этого замера не нужен, edit mode хватает.
   ⭐ `flip` — не только настенным: импорт Unity разворачивает кадр Blender на
   180° по вертикали (x → −x, y → −z), и предмет на поверхность без `flip`
   встаёт перёдом к стене, а ряд — зеркально (P564, 24.09). Все корни сцены с
   перёдом или порядком по x — через `flip`; после импорта сверить узлы.
   ⭐ Начало координат настенной модели — в СЕРЕДИНЕ глубины (19.09, мелочи
   ванной): если авторить «стена = z 0», пластина крючка на z −0.004 по знаку
   считается «в комнате», и проба краснеет на верной модели. Перед `flip`
   звать `centre_depth(root)` (сдвиг детей на середину габарита по глубине,
   образец `bath_towel_scene.py`); в `EXPECT` пробы брать ноды, явно
   лежащие по разные стороны середины, а не те, что на ней (носик крючка под
   полотенцем, палка швабры).
7б. ⭐ РАЗВОРОТ И ОСИ ЧАСТЕЙ — только спавн-пробой в play (P019, P020, P028),
   глазами в Blender не судить. Вешалка 09.09 уехала в игру рейками к игроку
   (перед объекта = локальный −Z), а дверцы крутились вокруг локального Z, а
   не Y, как у Kenney-моделей. Лечится в сцене: `flip()` на 180° вокруг
   вертикали при `params['export']`, как у навесного шкафа; ось части в дефе
   ставится по замеру «куда уехало полотно».
8. Запись в DESIGN_LOG + сюда; пойманный баг — `P…` в PITFALLS в тот же час.
9. ⭐ Картинка на модели (ковры `bath_rug`, договор `lease`): словарь `TEX = {слот: (png, имя ресурса)}`
   в сцене — `build_kit` сам копирует PNG в `Resources/<папка>/` и пишет `texture` в слот.
   Не квадратную картинку (лист A4 2048×2896) оставлять с `npotScale = ToNearest`: Unity
   ужимает её до 2048×2048 и жмёт BC7 (≈4 МБ), развёртка тянет её на весь лист, искажения
   нет. `npotScale = None` оставляет RGBA32 без сжатия (≈30 МБ) — так не делаем. Текст на
   текстуре — `maxTextureSize` 4096 и `anisoLevel` 8 (читается под углом осмотра).

## Грабли Блендера — индекс

| P | О чём |
|---|---|
| P014 | вотчеры: убитый shell, старое окно, старые киты |
| P017 | модель весит десятки тысяч треугольников |
| P018 | `isReadable=false`: вершины FBX нельзя читать даже в play |
| P019 | оси импортированной ноды не совпадают с осями Blender |
| P020 | знак и ось хода тумблера или створки — только замером |
| P021 | ось петли у узлов кита: вертикаль = локальная Z |
| P022 | экспорт унёс состояние просмотра: открытая дверца, запечённые цифры |
| P023 | Blender уникализирует имена: `Body.001`, второй `Lock` пропал |
| P024 | `object.join` теряет модификаторы и origin неактивных деталей |
| P025 | изнанка видна в Blender, но не в URP |
| P026 | совпадающие плоскости: z-fighting и «пила» |
| P027 | пустышки: масштаб и поворот после импорта врут |
| P028 | две конвенции импорта FBX — объект «вверх» или «к стене» |

  материалы каждого ребёнка корня (exec сцены с build-params, json), затем
  сравнить; FBX сверять импортом обратно в Blender — файлы бинарные, с
  таймстампом и в Git LFS (`git show` даёт указатель, бинарник лежит в
  `.git/lfs/objects/<oid[:2]>/<oid[2:4]>/<oid>`), размер/md5 не показательны.

**Ловушки (все поймано на практике):**
- FBX из Blender: Base Color линейный → srgb_to_linear при записи.
- **После `join` — `transform_apply(location, rotation, scale)`** (дерево,
  2026-08-27). Join оставляет объекту трансформ АКТИВНОЙ детали (у кроны —
  повёрнутая ветка), а Unity `Renderer.bounds` = AABB повёрнутого ЛОКАЛЬНОГО
  бокса, не вершин: высота 4.81 читалась как 5.75, след раздуло на метр.
  Меш в мировых осях ⇒ bounds 1:1 с Blender.
- `curve.extrude` растит ленту в направлении нормали кривой (для линии
  по гребню это ВЫСОТА, не ширина) — широкие ленты делать мешем.
- Торцы лент/лямок, встающих в тело под углом, вылезают «ушками» —
  топить концы ниже поверхности и следить за верхним силуэтом.
- pkill в той же команде убивает сам себя (паттерн есть в своей
  cmdline) — использовать скобочный трюк `pkill -f "имя_файл[а]"`.
- **Радиальный развал (ножки веером) euler'ом НЕ делается**: Blender крутит
  euler по МИРОВЫМ осям, и все элементы кренятся в одну сторону, а не каждый
  по своему лучу (поймано на столе 2026-08-14). Правильно — кватернион:
  `Vector((0,0,1)).rotation_difference(axis)`, где `axis` — направление
  своего луча. Ещё надёжнее задавать не угол, а ДВЕ ТОЧКИ (верх у центра,
  ступня у кромки) и считать ось/длину из них — параметры сразу читаемые
  («сходятся в центре на R=0.24, ступни на R=0.56»).
- ⭐ Объект С НОДАМИ (створки/рычаги) из Blender (2026-08-27, счётчик):
  экспорт с `apply_scale_options='FBX_SCALE_ALL'`, у импортёра Unity

  авторенная в игровом кадре через `to_blender`, ложится 1:1 без разворота

- Цвета json для объектов Kenney-палитры — сырые hex/255 (как `Kenney.Mat`),

## ⭐⭐ ПЕРЕНОС ОБЪЕКТА ИЗ BLENDER В ИГРУ 1:1 — эталонная процедура

Отработана на окне#1 (2026-08-16, переносили дважды: первый заход Илья
забраковал целиком — «перенос ужасный»). Пайплайн выше — про то, как объект
СОЗДАТЬ; этот — про то, как уже утверждённую блендер-модель довезти до игры
без потерь. **Любой перенос из эталонной сцены идёт по этим шагам.**

**0. Прочитать эталон целиком, включая ОКРУЖЕНИЕ.** Эталон — это функция в
`*_scene.py`, а не картинка. У встроенного в стену объекта половина работы —
то, чем сцена его окружает: у окна это `wall_with_openings` + `clad_piece` +
матрица материалов (`wall_x_mats`: наружная грань — сайдинг, ВНУТРЕННЯЯ —
`core_m`, торцы — `clad_m`). Пропустишь — объект приедет, а вид не сойдётся.

**1. Кит-сцена 1:1 с эталонной функцией — числа копировать, не «примерно».**
Систему координат эталона пересчитать в локальный фрейм кита ЯВНО и записать
пересчёт: у окна `fbox` менял местами оси, а глубина считалась от НАРУЖНОЙ
грани стены, тогда как кит живёт от середины (сдвиг −WALL_T/2).

**2. ⭐ Отрендерить кит с ТЕХ ЖЕ КАМЕР, что эталонные рендеры, и сравнить
картинки ДО единой правки C#.** `door_kit_preview.py` — образец: собирает кит,
ставит вокруг болванку стены с проёмом, снимает снаружи и изнутри камерами
из `plank_relief_scene.py`. Так поймали зеркальную створку; в Unity этот же
баг стоил бы часа отладки.

**3. Экспорт: FBX + json цветов рядом.** Цвета НЕ из материалов FBX (Unity
читает их как sRGB и они уезжают), а из `*-materials.json`; слоты
сопоставлять **по ИМЕНИ материала**, Blender экспортирует только
использованные слоты и переиндексирует их.

**4. ⭐ Ориентацию в Unity МЕРЯТЬ, а не выводить.** Blender→Unity здесь —
ОТРАЖЕНИЕ: `(bx,by,bz) → (−bx, bz, −by)`, определитель −1. Правая тройка
становится левой, поэтому «покрутить в голове» систематически врёт, а
картинка при этом выглядит правильной. Порядок: заинстанцировать кит в play с
тем же поворотом, что в коде, и снять `bounds` каждого куска — по
несимметричной детали (отлив) сразу видно, куда легли оси.

**5. ⭐ У стиля, приехавшего китом, процедурной геометрии быть НЕ ДОЛЖНО.**
Не «кит поверх старого», а ВМЕСТО. Ветка стиля выходит из билдера до
процедурной обвязки. Иначе — две рамы друг в друге, z-fighting и чужой
материал на половине объекта (ровно это и было «ужасным переносом»).

**6. Перенести окружение — по ПАРАМЕТРАМ, а не докидыванием мешей.**
Расхождение «текстур вокруг» почти всегда сидит в параметрах укладки обшивки,
эталон почти не строит декор отдельными объектами. Чек-лист параметров:
паттерн рядов, вынос, поперечные стыки (`JointGap`), отступ от кромки
(`startInset`), материал ПОД обшивкой (`core_m`), материал торцов/откосов.

**7. Проверить смежные плоскости на z-fighting.** У кита не должно быть
граней, лежащих РОВНО в плоскости стены/проёма/другой детали. Делать нахлёст
5–6 мм (отлив заходит ПОД раму). Правка — в эталоне и переэкспорт.

**8. Сверка в play с ракурса эталона, в обоих состояниях и с обеих сторон**
(закрыто/открыто, снаружи/изнутри). Расхождение лечим **правкой эталона +
переэкспортом**, никогда — подкруткой ассета в Unity.

**9. Жалоба на цвет ⇒ СНАЧАЛА ЗАМЕР.** Прочитать `_BaseColor`/`_Smoothness`
в play и сравнить с блендеровским. У нас «чёрная ручка» оказалась освещением
сцены при полностью совпадающем материале — правка была бы починкой света под
видом материала.

**10. Осознанные отступления от эталона фиксировать отдельно** в
`DESIGN_LOG.md` — с формулировкой «эталон делает так, мы решили иначе, потому
что…». Пример: стойки обшивки у нас только у проёма, в эталоне они и на
прогоне стен.

## ⭐⭐ ПРИНЦИПЫ ПЕРЕНОСА ОБВЯЗКИ — «текстур ВОКРУГ объекта»

Отдельный свод: на окне#1 (2026-08-16) сам объект перенёсся за один заход, а
всё остальное время съела ОБВЯЗКА. Правило Ильи: **переносим не только объект,
но и то, чем стена его обходит.** Ниже — то, обо что реально спотыкались.

**П1. Эталон — это СЦЕНА, а не объект.** Читать надо не только функцию
объекта, но и как сцена его окружает: чем режется стена (`wall_with_openings`),
чем обшивается каждый кусок (`clad_piece`) и какая матрица материалов у граней
(`wall_x_mats`). Половина работы лежит именно тут.

**П2. Сначала МОДЕЛЬ материалов, потом числа.** Сегодня пять раз крутили цвет
(0.56 / 0.78 / 0.80 / 0.95 / цвет доски / ×0.85 / ×0.75), а расхождение было в
том, КАКОЙ МАТЕРИАЛ НА КАКОЙ ГРАНИ: верх стены брал текстуру отделки вместо
тела стены. Починили модель — вопрос с цветом закрылся сам.
**«Цвет не такой» ⇒ сперва сверь раскладку по граням.**

**П3. «Текстуры вокруг» — это ПАРАМЕТРЫ УКЛАДКИ, а не отдельные меши.** Эталон
почти не строит декор объектами. Что выглядело как «доски, которых нет в игре»:
- вертикальные стойки у проёма = отступ обшивки от кромки (`CladInset`) плюс
  тело стены, видимое в этой полосе;
- вертикальные швы сайдинга = `JointGap` (был обнулён — фасад шёл сплошным);
- откосы = материал ТОРЦОВ куска (сабмеш 3), а не отдельная накладка.
Ищи расхождение в параметрах, а не в недостающих объектах.

**П4. Обшивка идёт ОДНИМ прогоном на кусок эталона.** Резать стену на куски
можно, резать ДОСКИ — нет: профиль доски начинается от плоскости стены заново,
и на каждом стыке кусков вылезает лишняя утопленная полоса. Над окном эталон
имеет один кусок до потолка, а игра — `Header` + `Lintel`, отсюда была плоская
полоса над окном (лечится `extraTop`).

**П5. Накладная отделка отсчитывается от ЛИЦА ДОСОК, а не от грани блока.**
Обшивка выступает на 7–9.4 см; плинтус с выносом 5 см, поставленный вровень с
гранью, исчезает целиком. Вынос обшивки отдаёт `PlankRelief.CladOut(tex)`.

**П6. Куски ПЬЕСЫ — не блоки сетки, и всё «поблочное» их не видит.** Плинтус,
покраска, дебаг-сетка работают по `GridBlock`; части проёма (косяки,
подоконная/надоконная стена, перемычка) — части пьесы, и каждую механику надо
провести по ним отдельно, иначе линия рвётся на каждом проёме.
⚠️ И помнить состав: **клетка проёма = подоконная стена + ДВА косяка по 0.5 м**
— кусок «по ширине подоконной стены» оставляет два провала.

**П7. Ориентацию и посадку МЕРЯТЬ, а не выводить.** Blender→Unity здесь
отражение `(−bx, bz, −by)`, определитель −1: правая тройка становится левой,
картинка при этом выглядит правильной, а рассуждение врёт. Инстанцировать в
play и снять `bounds` по несимметричной детали.

**П8. Цвет: одинаковые ЧИСЛА = одинаковый рендер.** И Blender (Base Color), и
URP (`_BaseColor`) берут ЛИНЕЙНЫЙ albedo, поэтому «одинаково» означает
одинаковые числа в `plank_relief_scene.py` и в коде игры. Hex при этом —
источник истины для человека, но в проекте он кладётся в материал СЫРЫМ
(плинтус, палитра Kenney), так что переведённый в linear hex в Unity даёт
почти чёрное. Меняешь цвет — меняй оба места и перерендеривай эталон.

**П9. Проверка — картинками с ОДИНАКОВЫХ камер.** Кит рендерить с камер
эталона ДО правок C# (`door_kit_preview.py`), в игре снимать с ракурса
эталона. Численная сверка — соотношение «деталь/фон» (у нас «выемка/доска»),
а не абсолютный цвет: освещение сцен разное.

**П10. Правка идёт в ЭТАЛОН и переэкспорт**, а не в ассет Unity. Исключение —
когда расхождение вызвано игровым освещением; тогда это осознанное отступление
и его пишем в `DESIGN_LOG.md`.

**П11. Природный объект едет ВАРИАНТАМИ, а не одним FBX** (2026-08-17, газон;
актуальная механика — 2026-08-28). Пятно дёрна, куст, камень ставят пачками —
одна форма на всех читается как copy-paste. Печём `<модель>01..NN` одним
прогоном экспортёра (`numbered()` в `pipeline.py`, список сидов в
`*_params.json`). В каталоге семейство — `Vegetation(idBase, name, model, n)`
+ константы `FurnitureCatalog.Trees/GrassTufts/GrassBushes/Sticks` и
`<X>Id`; вариант живёт в СУФФИКСЕ id (`veg_tree`, `veg_tree_2`…, `VariantId`/
`TryVariant`) и потому переживает сейв/лоад без полей в `LevelIO`. Вариант
выбирает Илья кнопкой «#n» (`HudUI.VariantButtons`) либо кисть травы —
случайно по весам. Прежний выбор хешем от позиции (`modelVariants`,
`FurnitureModel.VariantName`) из кода снесён аудитом мёртвого кода.

**П12. У периодической величины на замкнутом контуре фаза — от ДЛИНЫ ДУГИ,
а не от номера точки** (2026-08-17, кромка газона). Иначе частота волны едет
вместе с плотностью вершин: сделали ресемпл мельче ради гладкости — получили
шестерёнку. Считать `u = s[i]/total·2π` и брать ЦЕЛЫЕ гармоники — тогда контур
замыкается без стыка, а плотность точек и форма волны независимы.

**П13. Сливающийся объект: контур считает ГРУППА, рисует КАЖДАЯ клетка**
(2026-08-17, газон). Форм слияния бесконечно много — испечь их в FBX нельзя,
генератор едет в C#. Но и общий меш на группу не годится: `InteractiveObject`
строит коллайдер из `Combined(_renderers)`, и меш во всю поляну убил бы
выделение и снос отдельной плитки. Поэтому контур группы считается целиком
(один раз на пересборку), а плитка рисует его кусок. Размещение, сейв и снос
при этом не трогаются вовсе — слияние остаётся чисто визуальным.

**П14. Кусок берётся по БЛИЖАЙШЕЙ клетке, а не по своему квадрату**
(2026-08-17, пропавший борт газона). Контур выпирает за квадрат на амплитуду
шума, а скруглённая впадина внутреннего угла заходит в пустую диагональную
клетку. Резать по квадрату — значит срезать эти куски, причём срез ложится
ровно на линию реза, по которой борт НЕ строится: вдоль всех наружных выступов
борта не оказалось вовсе. Раздел по областям Вороного (полуплоскости к
имеющимся соседям) отдаёт наружные части кому-то всегда.
Отсюда общее: **«не рисуем на стыке» и «не рисуем на срезе» — разные вещи**,
признак внутреннего стыка обязан спрашивать про СОСЕДА, а не про геометрию реза.
Проверка такого объекта — замером: сумма длин борта по кускам обязана совпасть
с периметром общего контура.

**П15. Кромка от МИРОВОЙ точки, если группа пересобирается на лету**
(2026-08-17, газон). Фаза вдоль контура означает, что одна доставленная плитка
меняет форму всей поляны. Поле от координат локально, не требует сида вовсе и
переживает сейв/лоад без единого нового поля в `LevelIO`.

**П16. Пакетный режим для восстановления из сейва.** Если объект пересобирает
соседей, наивное восстановление даёт O(N²) — на сотне плиток газона вышло 727 мс.
`BeginBulk/EndBulk` вокруг восстановления объектов: внутри пакета ставятся только
баунды (по ним считается коллайдер), геометрия собирается один раз в конце —
37 мс на том же поле.

**П17. Модуль не выходит за свои клетки** (2026-08-17, газон садился на линию
сетки). Снап считает след из ГАБАРИТОВ модели: `ceil((size − 0.02) / 1 м)`.
Значит всё шире 1.02 м становится двухклеточным, а центр чётного следа — это
линия сетки, а не клетка. Органическая кромка обязана поджиматься внутрь на свою
амплитуду ПЕРЕД сглаживанием. Правило полезно и без снапа: модуль 1×1 не должен
залезать на соседнюю клетку, где стоит другой объект.

**П18. Признак «настоящая кромка» — ПОМЕТКА, а не геометрия** (2026-08-17,
дырки в газоне). Пока раздел был квадратным, «внутренний стык» можно было узнать
по тому, что ребро легло на линию реза. С дырками появился третий вид ребра —
перемычка, которая тоже ни разу не кромка, но ни на какой линии не лежит.
Держать признак флагом и переносить его через рез (кусок ребра наследует, новое
ребро вдоль реза — нет) короче и честнее, чем наращивать геометрические проверки.

**П20. Нормали — ЧАСТЬ ПЕРЕНОСА, а не деталь реализации** (2026-08-17, блик
газона вернулся). Перенося геометрию, легко перенести форму и отдать нормали
`RecalculateNormals()`. Для ворса это возврат известного бага: травинка —
пирамидка, нормали по граням смотрят вбок, сотни лезвий на м² дают поле
микро-зеркал и пятно вспыхивает белым (см. «Газон»). Задавать нормаль явно при выдаче
треугольника. Проверка: у накладки не-вертикальными обязаны остаться ТОЛЬКО
борты — замер «сколько нормалей вбок» против «сколько вершин в борту» должен
дать одно число.

**П22. В генераторе геометрии считать не только треугольники, но и МУСОР**
(2026-08-17, газон). Полная пересборка двора выбрасывала в сборщик 53 МБ при
той же геометрии. Три источника, и все три типовые для процедурных мешей:
на каждый мелкий элемент (травинку) создавались временные массивы; перевод
координат шёл через `System.Func`, то есть замыкание на объект и косвенный
вызов НА КАЖДУЮ ВЕРШИНУ; рабочие буферы резки и триангуляции создавались заново
на каждую клетку. После правки — 0.5 МБ и −26% времени при побайтно той же
геометрии (вершин ровно столько же). Проверять `GC.GetTotalMemory` вокруг
пересборки так же обязательно, как считать треугольники.
Отдельно: структуру-контекст передавать `in` и объявлять `readonly` — иначе
компилятор делает защитную копию на каждом обращении и выигрыш пропадает.

**П21. Крупный модуль = НАБОР клеток в реестре, а не одна** (2026-08-17, газон
2×2 и 3×3). Размеры нужны для скорости расстановки, вид обязан остаться тем же.
Если объект N×N пишется в реестр одной клеткой, он находит соседей только
центром и по краям даёт швы. Пишем все N² клеток, рисуем все N² куска в ОДИН
меш (у 3×3 это 5 дроуколлов вместо 45). Размер кодируем суффиксом id
(`veg_lawn_2`) — приём лифта: ни одного нового поля в `LevelIO`, старые записи
остаются одиночками. Смещение клетки от центра `2i − (N−1)` в полуметровых
ключах верно и для чётного N (центр на линии сетки), и для нечётного (центр в
клетке) — ровно так их и снапит `AxisSubSnap`.

**П19. Фигура с дырками сводится к простой перемычками** (2026-08-17, газон).
Обходим ВСЕ циклы границы (внешний — площадь > 0, дырки — < 0, материал у всех
слева), затем врезаем дырки в внешний контур по убыванию максимального x лучом
по +X: он упирается либо во внешний контур, либо в уже вшитую дырку, то есть
всегда в материал. Дальше работает обычная резка и триангуляция.
Грабли: перемычка ДУБЛИРУЕТ две точки, и ear clipping встаёт на них — совпавшая
с углом вершина считается «внутри уха». Пропускать вершины, совпадающие с углами
треугольника.

## ⭐⭐ ПЕРЕНОС РИСУНКА ИЗ BLENDER В ИГРУ — данными, а не правилом

_Отработано 2026-09-04 на тумане._

Третья процедура переноса, рядом с «объект 1:1» и «обвязка». Те две — про ОДИН
объект. Эта — про случай, когда эталон это не форма, а **расстановка**: десятки
элементов, у каждого своё место, размер, поворот и прозрачность (туман — 55
шаров на клетку и 10 на мост). Отработана на тумане, Илья: «давай попробуем
точно сделать прям рисунок» — и по итогу «получилось хорошо».

**Суть приёма: расстановку не ПОВТОРЯЮТ в коде теми же числами, а ВЫГРУЖАЮТ
файлом.** Правило-генератор в игре остаётся запасным путём на случай, когда
файла нет. Пока расстановка живёт двумя реализациями (питон в сцене и C# в
игре), они расходятся при каждой правке эталона, и расхождение не видно глазом
— видно только замером.

**1. Выгрузка: банк форм + таблица расстановки.** Один скрипт (`build_*.py`)
пишет рядом три вещи: FBX с формами, json с раскладкой и, если элементы
соединяются, json со стыком. Раскладка — список строк «позиция, масштаб,
поворот, цвет/прозрачность, флаги роли, ИМЯ МЕША в банке». Несколько вариантов
(у тумана 8) выгружаются одним прогоном с разными зёрнами, игра выбирает вариант
по координате клетки.

**2. Оси пересчитывать явно и записывать пересчёт.** У тумана
`x → x`, `z → y`, `-y → z`. Пересчёт живёт в одном месте выгрузки, а не
размазан по коду игры.

**3. ⭐ Читать БАЗУ, а не текущий кадр.** В анимированной сцене `ob.scale` и
`ob.location` отдают значение кадра, то есть ФАЗУ анимации. База берётся из
фкривой, тип цикла определяется по числу ключей: замкнутый синус (5 ключей) —
среднее первых четырёх, цикл «вырос-угас» (17 ключей) — пик. Флаг объекта тут
не помощник: один и тот же флаг может стоять и на дыхании, и на затухании
(P193).

**4. ⭐ Всё, что адресуется ПО ИМЕНИ, сеять фиксированным зерном.** Банк мятых
сфер сеялся зерном сцены — каждый вариант мял свои меши, и имя в раскладке
указывало на другую геометрию, чем в FBX. Отдельная константа `BANK_SEED`,
общая для всех вариантов и для выгрузки (P194).

**5. Масштаб приводить множителем FBX, а не нормировкой.** `lossyScale`
меш-трансформа в префабе (у нас 100) — это и есть перевод блендеровских единиц
в игровые. Нормировка «по первому мешу» кажется безопасной, но съедает
собственный размер каждой формы: у мятой сферы полуразмер не единица.

**6. ⭐⭐ СВЕРКА РЕНДЕРОМ — главное. Сначала ОДИН элемент, потом сцена.**
Порядок:
- в блендере построить сцену, снять анимацию (объектную И материальную —
  затухание живёт в узлах материала), выставить базовую позу, отрендерить
  ортокамерой на однотонном фоне;
- в игре поставить то же самое, погасить анимацию, снять тем же ракурсом
  (ортокамера + `RenderTexture` + `ReadPixels` → png);
- **сначала оставить по ОДНОМУ элементу** и сравнить медиану пикселя и ширину
  силуэта. Одиночный элемент отделяет ошибку ЦВЕТА от ошибки НАЛОЖЕНИЯ: пока
  один шар не сошёлся, сравнивать кучу бессмысленно;
- потом целая сцена: площадь силуэта, медиана, перцентили 10/50/90/99.
Числа тумана как образец: одиночное ядро 116 против 117, ширина 308 против
304 px, целая клетка 40.8 % против 40.8 % площади.

**7. ⭐ Отклик шейдера МЕРИТЬ сеткой, а не выводить из теории.** «Проект
линейный, значит цвет линейный» — ровно та ловушка, что стоила двух неверных
правок подряд. Правильный ход: прогнать сетку (цвет × альфа) через рендер,
записать пары вход→пиксель и посмотреть, какую функцию даёт движок. Так за один
замер выяснилось, что `MaterialPropertyBlock` отдаёт число как есть, а
URP/Unlit трактует `_BaseColor` как sRGB (P192). Тот же приём годится для любого
«в игре выглядит иначе».

**7а. ⚠️ Формула, верная в питоне, может тихо давать NaN в C#.** При переносе
любая ДРОБНАЯ СТЕПЕНЬ от синуса или косинуса обязана быть обёрнута в
`Mathf.Max(0f, ...)`: `Mathf.Sin(Mathf.PI)` в C# float равен −8.742e−08, то есть
ОТРИЦАТЕЛЕН, и `Pow` от него даёт NaN, тогда как в питоне `math.sin(math.pi)`
положителен. NaN не бросает исключение — он протекает в вершину, и Unity роняет
невнятный ассерт `Invalid worldAABB` вместо ошибки. Проверять перенос надо не
только в середине диапазона, но и НА ГРАНИЦАХ (u = 0 и u = 1): у ветра NaN был
ровно в одной точке из 41, а в середине всё сходилось идеально. Грабли P268.

**8. Что не переносится — записать явно, а не молча оставить.** У тумана это
ориентация граней: блендер правосторонний, Unity левосторонний, FBX меняет знак
X, и точный перенос поворота требует переэкспорта банка с зеркалом. На мятых
сферах не видно — отложено записью в `DESIGN_LOG.md`, а не «как-нибудь потом
вспомним».

**Порядок работы, если картинка не сходится:** замер → гипотеза → правка →
ПОВТОРНЫЙ замер тем же зондом. Три из четырёх причин расхождения тумана имели
правдоподобную, но НЕВЕРНУЮ первую гипотезу; отсеял их только повторный замер.

6. **Цвета** — тёмная гамма: корпус `#33363B`, детали/лямки `#1B1D20`;

### Общие помощники скруглённых форм в `blender_kit`

_2026-08-30._

**Дымовой тест сцен:** `blender -b --python BlenderWork/scene_smoke.py` строит
ВСЕ объекты реестра headless и печатает OK с числом треугольников, NOROOT или
FAIL; можно ограничить именами через `-- bed_double sponge`. Гонять после правок
`blender_kit` и перед переносом моделей. Замер геометрии до и после правки —
`scene_smoke.py` плюс проба из скретчпада (`geom_probe.py`), которая печатает
tris/verts/bounds конкретных корней.

`bevel_sharp(bm, offset, segments, angle)`, `rounded_outline(hu, hv, radii, arc)`
и `slab_bm(hu, hv, thick, radii, arc, bevel, segments, angle, top_scale)` живут в
`blender_kit.py`. Раньше их копии лежали в трёх сценах (кровать, стул, губка);
дедуп сверен замером: число треугольников и габариты не изменились (кровать
12312, стул 1036, губка 568). `radii` принимает число или четыре радиуса,
`top_scale` < 1 сужает верх (мягкая губка). Проверка при подобных правках:
headless-проба `scratchpad/geom_probe.py` (строит сцену по реестру и печатает
tris/verts/bounds корней) до и после, дифф должен быть пустым.

**Полая призма со скруглённым контуром** (2026-09-25, холодильник): корпус с
проёмом, ящик и балкон — один меш вместо 4–5 плит: `hollow_bm`, `prism_bm`,
`box_bm` (куб с весами на выбранных рёбрах — боковины плиты, у которой корпус
обязан остаться плитами ради составного коллайдера), `bm_object` и `rounded`
(Bevel + `harden_normals` + smooth) в `blender_kit.py`; образцы — `fridge_scene.py`,
`stove_scene.py`. Наружный и внутренний контуры — два
`rounded_outline` с одинаковым числом точек (радиус минус стенка), обод —
кольцо квадов; острые углы полости — веер треугольников от угла. Bevel-веса
кладём ТОЛЬКО на наружные петли: кромка проёма тоже выпуклая, отбор «по
выпуклости» скругляет и её (запись DESIGN_LOG 2026-09-25).

**Тело вращения с прямоугольным планом** (2026-09-20, корзина для белья):
`lathe(..., outline=fn)` — `fn(r, y)` отдаёт список точек кольца вместо
окружности, `seg` тогда не используется; `r` в профиле становится масштабом
плана. Скруглённый прямоугольник с сужением книзу — `plan_of` в
`laundry_basket_scene.py`: `rounded_outline(hw*k, hd*k, corner*k, arc)`, низ
`k=taper`. Углы лежат точно (по `arc` точек на угол), бок — один квад, поэтому
28 вершин на кольцо читаются ровнее 32-сегментного круга с `section`. Старые
сцены с кругом и `section` кит собирает теми же вершинами в том же порядке —
дымовой тест яблока, таза и флаконов после правки зелёный.

### Грязь кофейного набора в Blender
