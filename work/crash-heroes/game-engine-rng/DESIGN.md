## ТЗ «Концепт и техническое задание Dice RNG для Crash Games» — главный источник

Google Doc `1BrVa-nttkMrcrKpYJBk70laVOAwdgZvTqLX2SNlmtfE`
(https://docs.google.com/document/d/1BrVa-nttkMrcrKpYJBk70laVOAwdgZvTqLX2SNlmtfE/edit),
Илья прислал 18.09; читать через Google Drive (`read_file_content`). **Где ТЗ и макет
расходятся — прав ТЗ.** Суть:

- **Исход не зависит от банка**, P&L, других игроков, прошлых результатов. Банк и risk
  config — только для лимитов ставки, на выпавшую комбинацию не влияют.
- **Бросок двух d6, 36 равновероятных комбинаций; проигрыш — только 1-1, 3-3, 5-5**
  (не любой дубль!). P(crash) = 3/36 = 8.33 %, P(пройти раунд) = 11/12. Броски
  независимы. `dice_count`, `sides`, `loss_outcomes` — конфигурируемые.
- **Никакого заранее вычисленного crash_round.** Outcome выдаётся только после
  разрешённого Start/Continue/Fight; фронт только показывает.
- **Dice Outcome Service** — отдельный deployable microservice в контуре Crash Heroes,
  один на все сессии, два provider-а: внутренний CSPRNG (своя/тестовая модель) и
  адаптер лицензированного внешнего источника (authoritative в production; при его
  недоступности **нельзя** тихо подменять внутренним RNG). Для внешних событий хранить
  `source_event_id`, время, кости, match_id, players, move_number, evidence/video,
  подпись. Сервис не знает о банке, выплатах, Max Payout. Lucky Server — вне scope.
- **Сессия / «Экспресс»-купон на игрока**: Start (ставка) → backend проверяет лимиты
  → создаёт сессию со **snapshot** (bet, currency, math_version, таблица,
  final_multiplier, max_payout, max_bet) — неизменен до конца → первый round → после
  успеха Cash Out или Continue → Continue = ровно один новый round → crash-комбинация
  = ставка проиграна → после последнего (49-го) раунда — **автоматический Cash Out**
  по Final Multiplier.
- **Math Config**: `rng_type=dice`, `dice_count=2`, `sides=6`, `loss_outcomes`,
  **`rounds=49`**, **`rtp=97%`** (House Edge 3 % — производное). `Multiplier(N) = RTP /
  P^N`. Generate Math → проверка → Publish **Math Version** (immutable, draft /
  published / archived); начатые сессии живут на своей версии. Показывать target RTP,
  фактический RTP после округления и отклонение. Выплата считается **по опубликованному
  (округлённому)** коэффициенту, не по скрытому точному.
- **Базовая таблица (Cash Out) RTP 97 %, 49 раундов** — зашита в движке
  (`src/domain/coefficients.ts`), 1.0582 … 68.9305. **Сверено 18.09: все 49 = `round(0.97 /
  (11/12)^N, 4)`, отличий нет; фактический RTP по опубликованным значениям 96.997–97.002 %
  на раунд**; шанс пройти все 49 = 1.407 %.
- **Max Payout / Max Bet**: `Max Bet = Max Payout / Final Multiplier`, округление
  **вниз** до шага ставки ($30 000 / 68.9305 ≈ $435.22). Операторский потолок только
  строже: `Effective Max Bet = min(calculated, operator)`. Изменение Max Payout — только
  для новых сессий, не обрезает идущую лестницу. Max Exposure — отдельный risk-слой,
  исходы не трогает.
- **Config API** (snake_case): `game_mode`, `math_version`, `rtp`, `rounds`, `rng{type,
  dice_count, sides, loss_outcomes}`, `coefficient_table[{round, multiplier}]`,
  `final_multiplier`, `currency`, `max_payout`, `max_bet`.
- **Start** → минимум `session_id, bet, currency, math_version, max_payout, max_bet, level,
  current_multiplier, current_payout, can_continue, can_cashout`.
- **Continue/Fight** — запрос `session_id` + уникальный **`idempotency_key`**; ответ
  `round_id, dice_1, dice_2, result (win|crash), level, new_level, round_multiplier,
  cumulative_multiplier, current_payout, can_continue, can_cashout, session_status,
  math_version` (+ provenance для licensed). Повтор ключа → тот же ответ, без нового
  броска. **Cash Out** тоже идемпотентен → `final_multiplier, payout, session_status =
  completed`.
- **Locks**: на сессию один переход состояния одновременно (двойной клик, ретрай,
  параллельные Continue/Cash Out не должны перескочить два уровня или выплатить дважды).
- **История**: каждый round — session id, round id, level, кости, result, math_version,
  round/cumulative multiplier, payout state, idempotency key, timestamps. После Crash
  выделять последний проигрышный этап, успешные сохранять, будущие не показывать.
  Будущие коэффициенты показывать можно, будущие кости — нет.

## Что в макете

Две линии по 11–12 экранов, одинаковый флоу:

- **верхняя — хоккей. Её и делаем** (Илья: «мы хоккеиста делаем верхнюю линию»);
- нижняя — тот же флоу в другом скине (дзюдо, «Kalmar», тёмная тема) — **не наша**.
  Но подписи под её экранами описывают состояния — они ниже, в таблице.

Каждая линия — две ветки: **«Проигрыш»** (экраны 0–5) и **«Победа»** (6–15).
Номера с пропусками (нет 3, 7, 10, 13) — так в макете. Подписи «Референс ·
Winline / Fonbet» — чьи экраны взяты за образец.

## Механика (как читается из макета)

- Игрок выбирает **сумму** (чипы `All in`, `50`, `100`, `500`, `1K`, `5K`, `20…`;
  кнопки `x2` и `×` — удвоить / сбросить) и жмёт **Play**.
- Бросают **два кубика** — синий и красный (до броска на них «?»). Рядом в шапке
  — видео/анимация броска.
- **«Игра идёт до выпадения дубля»** — так в тексте макета. **По ТЗ проигрыш — только
  1-1, 3-3, 5-5**, не любой дубль. Лестница кф — из ТЗ (1.0582 → 1.1544 → 1.2593 → …),
  1.06 / 1.15 / 1.25 в макете — округление первых её значений.
- После выигранного раунда выбор: **«Забрать N»** (выкуп по кф выигранного
  раунда) или **Play** — бросать дальше за следующий кф.
- **Возм. выигрыш** до броска = сумма × кф ближайшего раунда (100 × 1.06 = 106).
- **Ставка списывается сразу на старте** (баланс 237 → 137 при ставке 100);
  выкуп зачисляется при «Забрать» (37 + 115 = 152).
- Выигрыш — модалка с кубком «Ты выиграл! 115».
- **«История бросков»** — лента чипов с кф прошлых игр (`3.02`, `1.16`…), у части
  — значок кубка; до первой игры — `???`.
- Картинка на льду иллюстрирует результат: раунд выигран — защитник падает,
  хоккеист проезжает дальше; дубль — падает хоккеист.

1. ~~Кф выглядят заглушками~~ — **снято ТЗ**: я исходил из «проигрыш = любой дубль»

   относительно экрана 12 («Раунд 2 · 1.15 / Раунд 3 · 1.25»).

   выигран; на хоккейном экране дубля нет.
5. Что значат чипы истории с кубком (выкуп?) и почему в истории `3.02` при лестнице
   1.06 / 1.15 / 1.25.

## Что это значит для движка — предположения, не решения

- Это **не краш с общим раундом на всех** (как 13 старых движков: один цикл
  ~14 с, все ставят в него). Здесь **у каждого игрока своя игра**: он сам жмёт
  Play, сам решает бросать дальше или забирать. Значит, состояние — на игрока
  (сессию), а не глобальный `currentRound`. Похоже, отсюда и `rng` в имени
  репо — игра на случайном броске, а не на кривой времени.
- Бросок — **не в движке и не на клиенте**: из потока dicestream (внешний источник по ТЗ),
  первый бросок после запроса, с `roll_id` и всем событием в БД для аудита/споров
  (решение 18.09, см. SKILL.md «Раунд и шаги»; `randomInt` в движке — отменено).
- **Клиент держит WebSocket прямо с движком** (решение 18.09, как у крашей, путь —
  uuid игры: `wss://dev.server.crash-heroes.com/<uuid>`). Сообщения `{type, data}`:
  ставка (сумма) → первый бросок; «бросать дальше»; «забрать»; история; баланс.
  Ответ на бросок — кубики, дубль или нет, текущий кф, сумма к выкупу. Игрока и
  деньги движок проверяет/проводит через api-core.
- Деньги — через api-core: списание ставки на старте, зачисление выкупа на
  «Забрать»; для партнёрских игроков — seamless (`bet` / `win`), см. скил
  `crash-games`. Проигрыш денег не двигает.
- Таблицы `game_crash_rounds` / `game_crash_bets` в api-core под это не
  подходят (там раунд общий и один коэффициент) — нужна своя модель: игра
  игрока → броски.
