## Открытые вопросы (Q)

- **Q1 — Имя таба склада.** ТЗ называет второй таб то «Неактивные» (Часть 1), то «Архив» (Часть 2, Дублирование, Черновик ч.2). Нужно единое каноническое имя + точное соответствие статус↔таб. *Влияние:* C2-2, навигация, фильтры.
- **Q2 — Полный маппинг статус↔таб.** Зафиксировать, какие статусы в каком табе и какие статусы вообще существуют (в т.ч. есть ли отдельный «Архив» как статус помимо таба). Перечни статусов в ТЗ местами расходятся.
- **Q3 — Канонический флоу создания.** Часть 2 («Паспорт», радио Родительская/Подвитрина, поля сразу) vs «Черновик второй части» (Этап 1 паспорт → Сохранить → Этап 2 конструктор, тумблер «Опубликовано»). Это две редакции одного флоу. Какая финальная? *Влияние:* вся Часть 2/3, кнопки Сохранить/Опубликовать vs тумблер.
- **Q4 — ЗАКРЫТ (2026-06-02) → см. R-1.** Архитектура статуса витрины: вычисляется на чтении, фоновый джоб не нужен.
- **Q5 — Параметр сортировки при склейке секций.** Дата создания подвитрин (новее выше) ИЛИ алфавит ID? Выбрать ОДИН и зафиксировать в коде (model.md §4).
- **Q6 — «Дублировать» — целевой таб.** В Архив/Неактивные (C2-2) — согласовать с Q1 после решения по имени таба.
- **Q8 — Reverse-lookup `getShowcases`: скан vs индекс (БЭК, перф).** gRPC `ShowcasesInternalServiceImpl.getShowcases` (батч по `content[]`) делает полный скан всех секций нужных типов + фильтр по `contentId` внутри JSONB `ELEMENTS` **в памяти** → `O(S·(E+K))`, доминирует `S` (скан). Батч по списку дешёвый (K — слагаемое), но сам скан не масштабируется. Решение зависит от **частоты вызова** (узнать у z0mb1ek): редко/админски → оставить, долг; горячий путь (рендер фида) → протолкнуть фильтр в БД (`SECTIONS.content_ids uuid[]` + inverted index `&&`, либо нормализованная `section_elements` с btree) → `~O(K·logN + M)`. Проверять оператор/индекс и на CockroachDB v26.2. Детали/анализ — в `Olimp-CMS/claude/tasks/CM-573-grpc-getShowcases-list.md` (локальный файл, не в коммите; из кода комменты убраны).
- **Q7 — Где живёт фича на бэке.** Какой сервис Olimp-CMS отвечает за витрины/секции/экраны и где граница с content (медиа/баннеры) через gRPC. Уточнить и записать сюда для маршрутизации задач. (Связано: ShowcaseService/SectionService/ScreenService, contentGrpcClient — набл. 3829–3844.)
- **Q9 — Per-language секции (отход от ТЗ, ТРЕБУЕТ согласования с Даней).** Принято (Илья) делать секции **привязанными к языку**: у каждого языка витрины свой отдельный набор секций — своя структура, порядок, имена, типы. Т.е. на RU может быть один набор секций, на KZ — совсем другой. **Это противоречит ТЗ:**
  - **Корнер 2 «Локализация названий секций»** — там модель «**одна** секция на все языки, у неё переводится **имя** по локалям; переключение языка ретранслирует имя той же секции».
  - **§3.5/3.6** — сетка секций общая для языков, локализуется только наполнение (элементы) + имена; «Скопировать контент» клонирует общую сетку.
  - **Инвертирует R-4** — там зафиксировано «у секций **нет** колонки языка, язык живёт в `section_elements.locale`». Новая модель: `sections.locale` есть, `section_elements.locale` убран.
  - **Статус реализации (бэк уже сделан):** БД — `sections.locale` + индекс, `section_elements` без `locale` (PK `section_id+element_id`), миграции схлопнуты в 1 файл/таблицу; домен (`SectionElements`-wrapper убран, `Section.locale`), `SectionService`/`ShowcaseWriteService` (copySections + удаление языка → `DELETE sections WHERE locale IN removed`)/`ShowcaseLifecycleService` (публикация: язык заполнен = есть секция этого locale с контентом) переписаны; тип **`CUSTOM` удалён**; jOOQ regen + `compileKotlin` зелёные. gRPC/события/мобайл-выдача и фронт — **НЕ трогались** (отложено).
  - **Что нужно:** подтверждение Дани, что бизнес-модель именно «независимые секции по языкам». При подтверждении — переписать **Корнер 2** и **R-4** под новую модель (→ перенести Q9 в R-N), доделать gRPC locale-aware + фронт. При отказе — откатывать бэк-изменения. *Влияние:* Корнер 2, §3.5/3.6, R-4, добавление/удаление языка, наследование подвитрин, дублирование, «Скопировать контент».

**R-5 (2026-06-10, Илья):** Навигация после создания витрины/подвитрины — **сразу открываем редактор созданной витрины** (конструктор, таб «Внешний вид»), а НЕ возврат в список. Частично закрывает Q3 в части пост-создания: флоу «паспорт → Сохранить → проваливаемся в конструктор» (как в «Черновике второй части», Этап 1 → Этап 2). Реализация (фронт): `PageCreateShowcase.tsx` → `onSave` ловит `{ id }` из `createShowcase`/`duplicateShowcase` мутации и `navigate` на `showcase.detail.to(...)` (родитель) или `showcase.sub.to(..., parentId, id)` (подвитрина). Распространяется и на дублирование (тоже создание копии-черновика). Старый редирект в список с `search: { tab: redirectTab }` удалён (вместе с мёртвыми `redirectStatus`/`redirectTab`). Касается только UI-навигации; корнеры/инварианты не затрагивает.

**R-4 (2026-06-09, Илья):** Удаление языка у витрины — **по канону, без каскада в подвитрины**. Рассматривался вариант каскад-удаления (язык+контент чистится у подвитрин), но отвергнут — оставлен Корнер **C4-parent-del**. Итоговая логика в `ShowcaseWriteService.updateShowcase` при изменении `language_codes`: (G1) если сама витрина `status=PUBLISHED` → ⛔ `400 showcase.language.published-not-editable`; (G2) если хоть одна подвитрина `status=PUBLISHED` → ⛔ `400 showcase.language.sub-published`; (G3, =C4-parent-del) если удаляемый язык декларирует подвитрина (`language_codes` содержит) → ⛔ `409 showcase.language.used-by-sub` с именем подвитрины. «Опубликована» = **хранимый** `ShowcaseStatus.PUBLISHED` (не вычисляемый display-статус). Чистка контента **только по самой редактируемой витрине** (каскада нет, т.к. G3 гарантирует, что подвитрины язык не используют): у секций **нет** колонки языка — язык живёт в `section_elements.locale`, поэтому «удалить секции на языке» = удалить `section_elements WHERE locale IN removed`, затем удалить **только те** секции, что были затронуты и остались без элементов **во всех** языках (пустые-ранее секции не трогаем). Снят язык-пункт из TODO layer-protection (app/segment ещё не сделаны). i18n-ключи добавлены в оба `messages*.yml` (`showcase.language.*`). `compileKotlin` зелёный. Поправлено: corners.md C4-parent-del (добавлен published-гард G1/G2 + уточнение про `section_elements`).

**R-3 (2026-06-04, Катя/продукт):** Свои секции подвитрины — **ТОЛЬКО зона «после»** родительского блока. Зона «до» **отменена** (перекрывает часть R-2 про «две зоны до/или после»). Порядок в конструкторе подвитрины всегда: **родительский блок (якоря) → свои секции**, своя секция не может встать выше родительского блока. Следствия для реализации: **знак `sort_order`/негативы НЕ нужны**, отдельное поле `zone` НЕ нужно — свои секции под `subId` хранятся обычными неотрицательными `sort_order` (0..N), parent-блок мёржится первым на чтении (фронт; публичный фид-рендер — отд. задача, R-2). Бэк (`saveSections`, index-based 0..N) **менять не надо**. Работа сводится к **фронту**: запретить перенос своей секции выше родительского блока (а не только «между») — `handleSectionDragEndWithAnchor` должен реджектить любой дроп, после которого хоть один родительский якорь оказывается *после* своей секции; `anchorIndex` фиксируется в 0, зона «до» как UI-возможность убирается. Интерливинг «между родительскими» по-прежнему ⛔ (как в R-2/C3-якоря). 2-я итерация (`after_parent_section_id`) остаётся отложенной и теперь касается только зоны «после». Поправлено: corners.md C3-якоря, C3-pod-*. 

**R-2 (2026-06-03, Илья + Катя/продукт) — ЧАСТИЧНО ОТМЕНЁН R-3 (зона «до» убрана):** Порядок секций в подвитрине. Родительские секции = **неподвижный непрерывный блок** (read-only, наследуют сортировку родителя как есть; подвитрина их не двигает/не редактирует/не удаляет/не скрывает). Свои секции подвитрины — в **две зоны: до блока и/или после блока**. Интерливинг «между родительскими» в **v1 НЕ делаем** — дорого/хрупко (потребовал бы привязки своей секции к ID родительской + правило подрезки при удалении этого якоря). Отложено во **2-ю итерацию** как якорно-относительная модель (`after_parent_section_id` + reflow-правило). Хранение v1: свои секции под `subId`, маркер зоны до/после (рекоменд. явное поле `zone: BEFORE/AFTER` + `sort_order` внутри зоны; альтернатива — знак `sort_order`: `<0` до, `≥0` после). Зоны к родительским числам **не привязаны** (не общая шкала) → устойчиво к пересортировке/удалению родительских секций. Мёрж в конструкторе можно на фронте (`getSections(parentId)` блоком + `getSections(subId)` по зонам); тот же порядок «до / блок / после» позже повторить в публичном фид-рендере на бэке (отд. задача). Поправлено: corners.md C3-якоря.

**R-1 (2026-06-02, Илья):** Статус витрины — две оси. Хранимая `ShowcaseStatus = DRAFT/PUBLISHED/HIDDEN` (колонка `status`, ставит человек). Вычисляемая `ShowcaseDisplayStatus = DRAFT/SCHEDULED/ACTIVE/FINISHED/HIDDEN` — НЕ хранится, считается на чтении из периода и `now()` в UTC. Фоновый джоб переходов `SCHEDULED→ACTIVE→FINISHED` **не нужен и не создан**. Таймзона — абсолютная: период `(локальное время + своя tz витрины)` → UTC-момент → сравнение с `now()`; статус глобальный, таймзона запрашивающего (профиль/локаль) в расчёт не входит, клиент время не передаёт (профиль-tz — фронтовая презентация). Чинит баг: `FINISHED` раньше нигде не выставлялся. Реализовано в `Olimp-CMS/showcases` (`ShowcaseStatus`/`ShowcaseDisplayStatus`/`ShowcaseStatusResolver`, консьюмеры на UTC-сравнение). `compileKotlin` зелёный, SQL прогнан на Postgres 18.4 и CockroachDB v26.2. **Бэкфилл существующих строк — РУЧКАМИ** (Илья делает сам в БД), Liquibase-миграции для этого нет: нужно `UPDATE showcases SET status='PUBLISHED' WHERE status IN ('SCHEDULED','ACTIVE','FINISHED')`, иначе старые строки роняют чтение (`ShowcaseStatus.valueOf("ACTIVE")` → exception). Поправлено: model.md §2 (две оси + таймзоны), Q4 закрыт.
