# Витрины — модель: роли, статусы, медиа, развилки

---

## 1. Ролевая модель (Часть 6)

4 уровня. Принцип: каждый следующий включает права предыдущего (кроме спец-функций Аудитора).

| Действие / Роль | Админ 👑 | Эдитор ✍️ | Аудитор 🔍 | Вьювер 👁️ |
|---|:-:|:-:|:-:|:-:|
| Просмотр экранов и витрин | ✅ | ✅ | ✅ | ✅ |
| Просмотр настроек (read-only) | ✅ | ✅ | ✅ | ✅ |
| Выгрузка отчётов / Экспорт | ✅ | ✅ | ✅ | ❌ |
| Создание и ред. контента | ✅ | ✅ | ❌ | ❌ |
| Публикация на прод (Live) | ✅ | ✅ | ❌ | ❌ |
| Удаление Экранов целиком | ✅ | ❌ | ❌ | ❌ |

- **Вьювер** — «смотрю, не трогаю». Кнопки создания (+Экран/+Витрина/+Секция) **физически скрыты**; все инпуты read-only; кнопки Сохранить/Опубликовать скрыты; D&D-грипперы скрыты.
- **Аудитор** — read-only как Вьювер, **плюс**: кнопки экспорта (CSV/Excel) и копирование тех. данных (⋮ → Скопировать UUID / System ID).
- **Эдитор** — полный цикл контента: создавать/редактировать/скрывать/архивировать/**публиковать** витрины и подвитрины. ⛔ НЕ может удалять Экраны целиком (кнопка скрыта/disabled).
- **Админ** — всё. Эксклюзив: кнопка «Удалить экран» (с каскадными корнерами C1-7). Опционально: управление составом Экранов и привязкой платформ.

> Связь с Casbin/бэком: роли проекта (`project_admin` и др.) + объекты `projects.*`, действия `read`/`write`/`manage`. Удаление моделируется как `write` на отдельном `.delete`-объекте, иерархии действий нет. При разметке прав витрин держи соответствие этой матрице.

## 2. Статусы и жизненный цикл

### Статусы Экрана (интеграция платформ)
- 🟡 **Ожидает** — создан в админке, ни одна прила не интегрирована. Экран ⛔ заблокирован (C1-3).
- 🟠 **Частично** — часть платформ подключена, часть ждёт (например, iOS подключён, Android ждёт). Экран открыт. Тултип на бейдже: «Подключено: iOS. Ожидает: Android» (Развилка 1).
- 🟢 **Подключено** — интеграция подтверждена, работает на проде.

### Две оси статуса (ЗАФИКСИРОВАНО, реализовано в бэке)

Статус витрины — это **две независимые сущности**, нельзя держать в одном поле:

| Ось | Тип | Значения | Где живёт |
|-----|-----|----------|-----------|
| **Хранимая (lifecycle)** | `ShowcaseStatus` | `DRAFT` / `PUBLISHED` / `HIDDEN` | колонка `status` в БД, ставит человек |
| **Вычисляемая (UI-бейдж)** | `ShowcaseDisplayStatus` | `DRAFT`/`SCHEDULED`/`ACTIVE`/`FINISHED`/`HIDDEN` | нигде не хранится, считается на чтении из периода и `now()` |

Бейджи и табы (вычисляемая ось):
- 🟢 **Активна** (ACTIVE) — PUBLISHED, `now` в периоде (или дефолтная без периода). Таб **Активные**.
- 🟡 **Запланирована** (SCHEDULED) — PUBLISHED, `now < start`. Таб **Активные**.
- ⚪️ **Завершена** (FINISHED) — PUBLISHED, `now > stop`. Таб **Неактивные**.
- 🔒 **Скрыта** (HIDDEN) — снята с публикации вручную (хранимое). Таб **Неактивные**.
- 🟠 **Черновик** (DRAFT) — создаётся, ещё не публиковалась (хранимое); даты необязательны (Развилка 2). Таб **Неактивные** (в ТЗ местами «Архив», см. decisions Q1).

Логика резолвера (`ShowcaseStatusResolver.resolve`): `DRAFT→DRAFT`, `HIDDEN→HIDDEN`, `PUBLISHED→` (startDate null → ACTIVE; now<start → SCHEDULED; stop!=null && now>stop → FINISHED; иначе ACTIVE).

> ✅ **Открытый вопрос Q4 ЗАКРЫТ (2026-06-02).** Статус НЕ материализуется и НЕ обновляется джобом — он **вычисляется на чтении** из периода в UTC. Фоновый шедулер `SCHEDULED→ACTIVE→FINISHED` **не нужен и не существует**. Бэк хранит только `DRAFT/PUBLISHED/HIDDEN`; временной бейдж считается резолвером. Старая материализованная модель (с её багом — `FINISHED` нигде не выставлялся) отрефакторена. Детали — decisions.md → Q4.

### Таймзоны — абсолютная трактовка (ЗАФИКСИРОВАНО)

- Период (витрины/баннера/`ElementPeriod`) хранится как `(локальное время + своя timezone)`.
- Бэк сворачивает в **абсолютный момент UTC** и сравнивает с `now()` (UTC). Статус **глобальный** — одинаков для всех, зависит от *когда* спрашивают, а не *кто*.
- Таймзона запрашивающего (профиль админа, локаль клиента) в расчёт статуса **НЕ входит**. Клиент/админка **НЕ передаёт своё время** в запрос.
- **Guardrail:** код, подмешивающий таймзону профиля/клиента в вычисление статуса, — нарушение модели.
- Показ дат на фронте: период (есть своя зона) — дословно в зоне витрины, без конверсии, с подписью зоны; абсолютные метки (created/updated) — в таймзону профиля. Это чисто фронтовая презентация.
- SQL-сравнение в бэке: `(date + time) AT TIME ZONE COALESCE(timezone,'UTC')` vs `now()` (проверено на Postgres 18.4; на CockroachDB локально — перепроверить синтаксис `date + time` / `AT TIME ZONE`).

### Тумблер «Опубликовано» (Черновик ч.2)
- ВКЛ → витрина доступна API в рамках периодов активности.
- ВЫКЛ → полностью скрыта с прода, независимо от наполнения.
- Сохранить в опубликованной → **моментальный** апдейт прода (INV-PROD-NOW).

## 3. Медиа и платформы (раздел «Добавление Медиа в Витрины»)

**Базовое правило:** Веб и Мобайл (iOS, Android) — два изолированных лагеря, никогда не пересекаются. Витрина/баннер — либо Веб, либо Мобайл (одна или обе ОС). → INV-WEBMOBILE.

1. **Паспорт баннера (Библиотека):** при создании выбираются платформы — Веб, либо iOS/Android/обе. Система запоминает, где баннер физически может работать. (M-1)
2. **Фильтр в витрину:** видны баннеры с ≥1 совпадением по платформам (M-2). Примеры:
   - Витрина Веб → только веб-баннеры.
   - Витрина iOS+Android → «только iOS», «только Android», «iOS+Android».
   - Витрина только-iOS → «только iOS» и «iOS+Android».
3. **Авто-выключение (M-3):** узкий баннер в широкой витрине — система сама гасит неподдерживаемую платформу (серая/перечёркнутая иконка + тултип «Отключено: сам баннер не поддерживает эту платформу»). Менеджеру ничего удалять не надо.
4. **Защита от дурака в Библиотеке (M-4):** ⛔ нельзя снять платформу у баннера, который уже используется в витрине. Кнопка Сохранить блокируется, алерт «…используется в Витрине {Название}. Сначала удалите его оттуда».

## 4. Сортировка секций при склейке подвитрин

Когда юзер попадает в несколько сегментов, контент доступных ему подвитрин **склеивается в одну ленту** → возможен конфликт позиций секций.

- **Правило разрешения коллизий:** бэкенд применяет жёсткое системное правило. По умолчанию — сортировка по **дате создания подвитрин** (новее выше) ИЛИ по алфавиту ID подвитрин.
- 📌 **Для разработки:** выбрать и **зафиксировать в коде ОДИН неизменный параметр**. См. decisions.md → Q5 (что выбрали).
- UI-подсказки против ошибок таргетинга:
  - В настройках подвитрины: «Пользователь должен входить в сегмент Родительской витрины, чтобы увидеть этот слой».
  - В конструкторе подвитрины: «Контент наслаивается поверх базовой витрины. Если пользователь состоит в нескольких сегментах, он увидит контент из всех доступных ему подвитрин».

## 5. Развилки (обоснования решений менеджера)

- **Развилка 1 — статус «Частично».** Проблема: Android подключили, iOS нет. Оставить «Ожидает» → менеджеры не наполняют, iOS-юзеры видят дыру. Поставить «Подключено» → думают, что всё готово. Решение: промежуточный статус **Частично** + тултип с детализацией по платформам.
- **Развилка 2 — статус «Черновик».** Менеджер собирает витрину, не зная дат запуска. Решение: для черновиков **даты необязательны**; обязательность периода включается только при публикации (C3-react-4).
